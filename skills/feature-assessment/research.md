# Technical scan для Feature-assessment

Читать **после ownership**, до оценки подхода и estimate. Не превращать в полный architecture research и не подменять `solution-research`.

Нормальный flow:

```text
нормализованная потребность → прямые ссылки → целевой поиск → аналоги / код по режиму → стоп
```

Остановиться, когда можно сказать, что уже есть / чего нет, или становится понятно, что без глубокого research оценка безответственна.

## Глубина по режиму

### quick

Ограниченный scan. Цель: помочь ответить на входящий запрос за несколько минут.

- 3–5 минут research;
- прямые ссылки, 2–4 целевых запроса, точечный код только если путь очевиден;
- не делать глубокий code archaeology;
- не строить design package;
- не обходить несколько репозиториев «на всякий случай».

### deep

Более подробный assessment перед rough estimate.

- до ~10 минут;
- можно пройтись по нескольким репозиториям и аналогам;
- всё ещё не заменяет `solution-research`;
- не писать спецификации, контракты и выбранную архитектуру.

Если даже `deep` не даёт уверенности → `NEEDS_SOLUTION_RESEARCH`. Не натягивать `ESTIMATABLE`.

## Источники

Искать в таком порядке:

1. Jira / Story / прямые ссылки из входа;
2. Confluence — несколько целевых запросов;
3. связанные feature notes (`notes/features/…`, только явно релевантные файлы);
4. локальные репозитории — только доступные в workspace или явно указанные пользователем;
5. похожие существующие реализации.

Не ходить по всем проектам на диске. Не читать весь `features/` и весь `teams/`.

Карты ответственности в scan не искать.

## Что искать

- существующие механизмы;
- похожие фичи;
- текущие точки интеграции;
- reusable компоненты;
- фильтры / сегментацию / ranking / contracts / shared clients;
- потенциальные ограничения (совместимость, отсутствие контракта, чужой сервис).

Список выше — ориентир, не чек-лист для копирования. Искать только то, что относится к потребности.

## Чего не искать

- полный список потребителей каждого метода;
- все версии контракта;
- новую архитектуру «как правильно»;
- несколько альтернативных дизайнов ради количества;
- глубокий impact analysis;
- код и документы по подзапросам с `OTHER_TEAM_LIKELY` / `UNKNOWN`, если нет отдельной причины.

## Код

Разрешено подтверждать `FACT`:

- механизм / компонент существует;
- есть общий клиент / фильтр / контракт;
- текущее поведение устроено определённым образом.

Нельзя на основании короткого scan:

- выбрать архитектуру;
- объявить найденный аналог обязательным способом;
- перечислить конкретные endpoint / таблицы / поля как обязательный scope, если это не подтверждено;
- закрыть неизвестность догадкой.

Нет доступа к коду — не выдумывать устройство системы. Зафиксировать ограничение scan и понизить confidence или verdict.

## Более простой путь

Главный вопрос scan: можно ли закрыть потребность существующим механизмом, а не предложенным новым решением.

Если да (хотя бы как правдоподобная `OPTION`):

- показать этот путь **до** оценки предложенного подхода;
- объяснить, почему его стоит проверить первым (меньше новых интеграций, один слой, уже есть аналог);
- не выдавать его за выбранное решение.

Пример направления, не шаблон под все запросы:

```text
Потребность: ограничить видимость SKU по сегменту.
Предложено: проверять segment ↔ SKU.
Быстрый scan показывает, что вероятно можно решить через существующий механизм фильтрации каталога. Этот вариант стоит проверить первым, потому что он потенциально требует меньше новых интеграций.
```

## Когда scan обязан сдаться

Переходить к `NEEDS_SOLUTION_RESEARCH`, а не к грубой оценке, если:

- неясно, существует ли reusable механизм, и от этого сильно зависит стоимость;
- предложенный путь требует нового сервиса / ranking / ML / нескольких команд, и нет даже грубой карты;
- конфликт источников по текущему устройству без evidence;
- `deep` исчерпан, а уверенность всё ещё низкая для диапазона.

Не маскировать это списком вариантов.
