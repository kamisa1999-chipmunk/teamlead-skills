# Ownership для Feature-assessment

Читать **после нормализации**, до technical scan. На первой версии отдельную карту ответственности команд **не создавать и не подгружать**.

Не делать вид, что skill знает оргструктуру лучше пользователя. Если ownership не подтверждён — уточнить у пользователя.

## Статусы

Для каждого подзапроса — ровно один статус.

| Статус | Когда |
| --- | --- |
| `OURS_CONFIRMED` | явное подтверждение пользователя этого прогона, либо однозначный источник, который пользователь не оспаривает |
| `OURS_LIKELY` | осторожный inference из Jira / документации / контекста; не подтверждено |
| `SHARED` | затрагивает нашу зону и чужую; границы не схлопывать в «всё наше» |
| `OTHER_TEAM_LIKELY` | по контексту похоже, что основная зона другая; конкретную команду не выдумывать |
| `UNKNOWN` | оснований недостаточно |

Несколько инициатив в одном входе — оценивать ownership **по каждой отдельно**. Общий verdict тогда часто `MIXED`.

## Приоритет источников

1. явное подтверждение пользователя;
2. связанная Jira / Story;
3. найденная техническая / продуктовая документация;
4. осторожный inference.

Пользовательский комментарий бьёт текст треда, если они расходятся.

Пример: «пункт 2 точно наш, остальные под вопросом»:

- пункт 2 → `OURS_CONFIRMED`;
- остальные → `UNKNOWN` или максимум `OURS_LIKELY` / `OTHER_TEAM_LIKELY` по контексту, с пометкой гипотезы;
- не назначать остальные другим командам без подтверждения.

## Чего не делать

- не требовать заранее заполненную карту ответственности;
- не придумывать конкретную owning team без основания («это точно команда X»);
- не повышать `INFERENCE` до `OURS_CONFIRMED`;
- не считать компонент Jira / лейбл / assignee автоматическим proof, если пользователь сказал, что зона под вопросом;
- не писать «не наше, пусть делает команда N», если N не следует из источника.

Если команда названа в Jira / документе — можно указать как найденное, с provenance `FACT` (так написано) или `INFERENCE` (мы так поняли). Это не подтверждение пользователя.

## Влияние на глубину scan

| Ownership | Technical scan |
| --- | --- |
| `OURS_CONFIRMED` / `OURS_LIKELY` | обычный scan по режиму |
| `SHARED` | scan нашей части; чужую не раскапывать вглубь |
| `OTHER_TEAM_LIKELY` | без глубокого research, если нет отдельной причины |
| `UNKNOWN` | не углублять, пока не уточнили; вопрос пользователю |

Отдельная причина копнуть чужой кусок: пользователь явно просил оценить весь пакет; без этого нельзя понять, SHARED это или нет.

Если основной scope вне зоны пользователя → verdict `OTHER_TEAM`, без rough estimate по чужой работе.

## Как показывать

Компактно, по подзапросам. Статус можно оставить id — он короткий и однозначный.

```text
- Пункт 2 — показ SKU по сегменту: OURS_CONFIRMED (пользователь)
- Пункт 1 — смена витрины бренда: UNKNOWN; по эпику похоже на другую зону (гипотеза, не назначать)
```

Не разворачивать в оргсхему.
