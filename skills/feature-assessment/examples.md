# Примеры Feature-assessment

Читать только если нужен образец формулировок. Не подставлять примеры в живой assessment как факты. Не оптимизировать разбор под эти кейсы и не использовать реальные CAT2 из обсуждения скилла.

## Команды

```text
прикинь, как это сделать и сколько примерно займёт
feature assessment
разбери запрос из Mattermost
вот скрин треда, это наша зона?
оцени фичу по этой Story
deep assessment по этому запросу
набросай ответ в тред
```

Комментарий пользователя учитывать с высоким приоритетом:

```text
Вот скрин. Пункт 2 точно наша зона ответственности, остальные под вопросом.
```

## Quick: потребность vs предложенное решение

Вход: «Нужно, чтобы SKU были видны только своему сегменту. Давайте заведём проверку segment ↔ SKU».

Внутренне: потребность отдельно, проверка segment ↔ SKU = `OPTION`, не выбранное решение.

```markdown
Что просят
Ограничить видимость SKU по сегменту пользователя.
В треде предложено: проверять соответствие segment ↔ SKU.

Ownership
OURS_LIKELY — гипотеза по связанной витрине; пользователь зону не подтверждал.

Что уже есть
Похоже, в каталоге уже есть механизм фильтрации выдачи. Прямой проверки «segment ↔ SKU как отдельный сервис» не видно. Это не доказательство отсутствия.

Варианты
1. Проверить существующую фильтрацию каталога — стоит первым: меньше новых интеграций.
2. Предложенная явная проверка segment ↔ SKU — только если фильтрации недостаточно.

Предварительный scope
- backend: likely
- admin: possible
- web / iOS / Android: possible, если контракт выдачи не меняется — not relevant как отдельная работа
- contracts: possible

Что удешевляет / усложняет
Упрощает: существующий reusable механизм фильтрации; изменение в одном слое.
Усложняет: если фильтрации нет и нужен новый контракт / отдельная проверка на всех клиентах.

Вопросы
Блокирующие:
- Сегмент уже участвует в фильтрации каталога, или это новое правило?
Неблокирующие:
- Нужна ли ручная привязка SKU к сегменту в админке?

Verdict
ESTIMATABLE

Rough estimate
M, или предварительно 1–2 спринта, confidence medium

Assumptions
Оценка предполагает, что можно опереться на существующую фильтрацию каталога, новый сервис не нужен, старые клиенты сохраняют текущее поведение выдачи.
Если фильтрации нет и нужен отдельный сервис / новый контракт — верхняя граница уходит в L/XL, лучше NEEDS_SOLUTION_RESEARCH.
```

Плохо в этом же кейсе: сразу оценивать «сервис проверки segment ↔ SKU» как единственный путь.

## Mixed ownership

Вход: скрин из трёх пунктов + комментарий «пункт 2 точно наша зона, остальные под вопросом».

```markdown
Что просят
1. Сменить витрину бренда на главной.
2. Ограничить видимость SKU по сегменту.
3. Добавить персональный ranking выдачи.

Ownership
- 1: UNKNOWN; по контексту треда может быть чужая зона — гипотеза, никому не назначать.
- 2: OURS_CONFIRMED (пользователь).
- 3: UNKNOWN; ranking/персонализация часто shared / другая зона — гипотеза.

Что уже есть
По пункту 2: есть механизм фильтрации каталога, его стоит проверить первым.
По пунктам 1 и 3 глубокий scan не делался.

Варианты
Только пункт 2: сначала существующая фильтрация, не новая проверка segment ↔ SKU.

Предварительный scope
Пункт 2: backend likely; admin possible; клиенты possible.
Пункты 1 и 3: не оценивались.

Что удешевляет / усложняет
По пункту 2: удешевляет reusable фильтрация; усложнит отдельный сервис и контракт.
По пункту 3 само по себе удорожает любой пакет (ranking / ML / персонализация) — не смешивать с оценкой пункта 2.

Вопросы
Блокирующие:
- Пункты 1 и 3 берём в этот разбор или только пункт 2?
Неблокирующие:
- Для пункта 2 сегмент уже есть в фильтрации?

Verdict
MIXED

Rough estimate
Только пункт 2, не весь скрин: M / 1–2 спринта, confidence medium — если подтвердится фильтрация.
Пункты 1 и 3 без подтверждения ownership и без research не оценивать.
```

Плохо: поставить всему скрину одну оценку XL. Плохо: написать «пункт 1 — команда витрины».

## Когда оценки нет: NEEDS_SOLUTION_RESEARCH

Вход: «Сделайте персональную выдачу: новый сервис ранжирования, отдельный контракт на все клиенты, плюс миграция исторических предпочтений. Прикинь сроки». Deep scan не подтвердил, есть ли пригодный ranking-контур и кто им владеет.

```markdown
Что просят
Персонализировать выдачу каталога.
В треде предложено: новый ranking-сервис, новый контракт на клиенты, миграция предпочтений.

Ownership
UNKNOWN / возможен SHARED. Пользователь зону не подтвердил; конкретную команду не назначать.

Что уже есть
Короткий scan не подтвердил готовый механизм, который закрывает потребность без нового контура. Найденные упоминания ranking не сходятся между собой — конфликт источников, правильный вариант не выбирался.

Варианты
Предложенный новый сервис — OPTION, не выбранное решение.
Существующий более простой путь по scan не подтверждён.

Предварительный scope
- data / ranking: likely
- contracts: likely
- web / iOS / Android: likely
- backend / BFF: possible
Маркеры не confirmed: это предварительная карта, не факт.

Что удешевляет / усложняет
Усложняет: новый сервис / новая интеграция; изменения на всех клиентах; ranking / ML / персонализация; миграции данных; возможный shared ownership; неясные контракты.
Упрощающего reusable механизма scan не нашёл.

Вопросы
Блокирующие:
- Это точно зона нашей команды, или только потребитель ranking?
Неблокирующие:
- Миграция исторических предпочтений обязательна для первой версии?

Verdict
NEEDS_SOLUTION_RESEARCH

Rough estimate
Нет. Даже deep-режима недостаточно: стоимость скачет от «встроить в текущий контур» до «новый сервис + миграция + все клиенты». Это уже solution-research, не входной assessment.
```

Плохо: написать «примерно XL, 4–6 спринтов» и спрятать неуверенность в процентах.

## Ответ для треда

Только заготовка, не отправка.

```text
Предварительно выглядит как изменение существующего механизма фильтрации каталога, а не новый сервис сверки сегмента и SKU.
Основной объём — backend, админка под вопросом, клиенты скорее минимально.
Если фильтрацию можно переиспользовать, грубо 1–2 спринта. Если понадобится отдельный сервис или новый контракт — будет больше.
Нужно уточнить: сегмент уже участвует в фильтрации? админка для привязки SKU нужна в первой версии?
Это не оценка команды, только предварительный разбор.
```
