# Формат результата Feature-assessment

Читать **перед первым пользовательским выводом**. Не читать в начале прогона.

Результат должен быть компактным и пригодным для быстрого чтения. Внутренний чеклист pipeline, лог поиска и полную разметку provenance не показывать, если не просили технический отчёт.

Русские названия блоков. Id статусов ownership и verdict оставлять как есть — они однозначные.

## Структура

```markdown
Что просят
…

Ownership
…

Что уже есть
…

Варианты
…

Предварительный scope
…

Что удешевляет / усложняет
…

Вопросы
…

Verdict
ESTIMATABLE | NEEDS_ANSWERS | NEEDS_SOLUTION_RESEARCH | OTHER_TEAM | MIXED

Rough estimate
…   ← только если ESTIMATABLE

Assumptions
…   ← если есть оценка или оценка зависит от допущений
```

Блок «Варианты» опустить, если предложенного способа не было и skill не нашёл отдельного направления — не выдумывать альтернативы.

«Ответ для треда» — только если пользователь просил или это явно полезно для ответа в Mattermost. Не отправлять.

## Что просят

Потребность, не реализация. Если автор предложил способ — одним предложением отдельно: «В треде предложено: …». Это `OPTION`.

Несколько инициатив — маркированный список, не один абзац.

## Ownership

По каждому подзапросу: статус + короткое основание (пользователь / Jira / гипотеза).

Не назначать чужую команду без источника.

## Что уже есть

Факты и сильные inference из scan: существующий механизм, аналог, дырка в контракте, отсутствие найденной спецификации.

`не найдено skill'ом` ≠ `документа / механизма нет`.

## Варианты

Сначала более простой / естественный путь, если он найден. Затем предложенный автором. Затем максимум ещё одно направление, если оно реально следует из scan.

Не генерировать несколько вариантов ради количества. Не выбирать решение за команду.

## Предварительный scope

Только релевантные области. Маркер: `confirmed` / `likely` / `possible` / `not relevant`.

Не превращать `likely`/`possible` в факт. `not relevant` — если это снимает ожидание из запроса.

## Что удешевляет / усложняет

Два коротких списка. Только факторы, которые относятся к этому запросу. Универсальный список не копировать.

## Вопросы

1–5 коротких. Разделять:

```text
Блокирующие:
- …

Неблокирующие:
- …
```

Пустой блок не держать.

## Verdict

Ровно один общий статус. Для `MIXED` — общий `MIXED`, внутри Ownership/Что просят уже видно разложение.

| Статус | Оценка |
| --- | --- |
| `ESTIMATABLE` | дать rough estimate |
| `NEEDS_ANSWERS` | оценки нет; ждать ответы |
| `NEEDS_SOLUTION_RESEARCH` | оценки нет; нужен глубокий research, не этот скилл |
| `OTHER_TEAM` | оценки нет по чужой работе |
| `MIXED` | общей оценки нет; оценку по нашей части давать только если эта часть сама `ESTIMATABLE` — тогда явно подписать, что оценка не на весь пакет |

Не ставить `ESTIMATABLE`, если blocking-вопросы открыты или scan не закрыл развилку, которая меняет порядок стоимости.

## Rough estimate

Только при `ESTIMATABLE`. Диапазон, не точное число.

Предпочтительный формат: `S` / `M` / `L` / `XL`.

Если пользователь явно просит спринты — диапазон в спринтах:

```text
Предварительно: 1–2 спринта, confidence medium.
```

Ориентир размера (не шкала команды и не обещание):

| Размер | Смысл |
| --- | --- |
| `S` | локальное изменение, один слой, существующий механизм |
| `M` | несколько точек, но путь понятен |
| `L` | несколько слоёв / клиентов или заметная совместимость |
| `XL` | новый сервис, широкая интеграция, ranking/ML, сильный shared ownership |

Confidence только `low` / `medium` / `high`. Без процентов.

Не маскировать под командную оценку. Префикс вроде «предварительно» / «грубо» обязателен по смыслу.

## Assumptions

Обязательно, если есть оценка.

```text
Оценка предполагает, что:
- можно использовать существующий механизм X;
- не нужен новый сервис;
- изменения контрактов ограничены Y;
- старые клиенты сохраняют текущее поведение.
```

Если один из assumptions не подтверждается — указать, как меняется оценка (размер, верхняя граница или смена verdict на `NEEDS_SOLUTION_RESEARCH`).

Писать только те assumptions, на которых стоит эта оценка.

## Ответ для треда

Не отправлять сообщение автоматически.

Готовить короткую версию, если пользователь просит ответить в тред / Mattermost, либо если сам предлагает «набросай ответ».

Без внутреннего жаргона статусов, без лога поиска. Можно оставить диапазон и оговорки.

Пример тона:

```text
Предварительно выглядит как изменение существующего механизма X.
Основной объём — backend + admin, клиенты затрагиваются минимально.
Если можно переиспользовать Y, оценка порядка 1–2 спринтов.
Если потребуется отдельный сервис / новый контракт — будет больше.
Нужно уточнить два вопроса: ...
```

Не писать «команда оценила», «берём в работу», «это точно S», если пользователь этого не говорил.

## Показ

```text
Режим: quick | deep

…блоки структуры…

Следующий шаг (если уместно, не запускать):
- story-prep — если нужна нормальная Story
- solution-research — если verdict NEEDS_SOLUTION_RESEARCH
- уточнить ownership — если UNKNOWN / MIXED
```

`sa-task-prep` предлагать только если уже есть DeliveryStory и пользователь хочет постановку аналитику — не как следующий шаг по умолчанию.
