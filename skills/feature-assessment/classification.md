# Классификация для Feature-assessment

Читать **на шаге нормализации**, до ownership и technical scan. Это внутренняя модель. Не показывать пользователю целиком без необходимости.

Не путать с классификацией `story-prep` (`REQUIREMENT` / `CONSTRAINT` / `SOLUTION_HYPOTHESIS`). Здесь нет постановки Story: цель — отделить потребность от реализации и не повышать источник.

## Нормализация

Сначала разложить вход, не оценивая решение.

### Проблема / потребность

Что хотят получить с точки зрения поведения продукта или системы.

Писать как наблюдаемый результат для пользователя / бизнеса / системы, без привязки к способу.

### Предложенное решение

Если автор запроса уже предложил технический способ.

Сохранить, не потерять, не принять как выбранное. Это `OPTION`, пока нет подтверждённого решения.

### Ограничения / контекст

Что уже известно из сообщения пользователя, Jira, Confluence или предыдущего контекста диалога.

Только то, что реально есть в источниках. Не дописывать «очевидные» ограничения.

### Неизвестное

Что пока неясно и влияет на ownership, путь реализации или оценку.

Кандидат в вопросы, если ответ нельзя достать из доступных источников.

Если запрос состоит из нескольких инициатив — нормализовать каждую отдельно. Не сливать разные потребности в одну «фичу».

## Метки provenance

Каждое существенное утверждение внутренне пометить одной меткой. В ответе отражать уровнем языка, не таблицей тегов.

### FACT

Подтверждённый факт о текущей системе, процессе, карточке или явно данном ограничении.

Нужны evidence: исходный материал, документ, Jira или дозированная проверка кода.

Неподтверждённое «сейчас так устроено» — `ASSUMPTION` или `INFERENCE`, не `FACT`.

### USER_INPUT

Комментарий, уточнение или приоритет от пользователя этого прогона.

Высокий приоритет для ownership и scope. Не равен командному решению и не равен согласованному requirement.

Плохо: `команда подтвердила, что пункт 2 наш`.

Хорошо: `пользователь подтвердил: пункт 2 — наша зона`.

### ASSUMPTION

Принято, чтобы сдвинуться дальше, но не подтверждено.

Если оценка зависит от assumption — вынести в блок «Assumptions». Если assumption не подтвердится — сказать, как меняется оценка / verdict.

### INFERENCE

Осторожный вывод из контекста, связанной Jira, документации или кода.

Маркировать как гипотезу. Не писать как факт. Ownership по inference — `OURS_LIKELY` / `OTHER_TEAM_LIKELY` / `SHARED`, не `OURS_CONFIRMED`.

### OPTION

Возможный способ реализации: предложен автором треда, пользователем или найден как аналог.

Найденный аналог ≠ обязательный способ реализации. Предложение автора треда ≠ выбранное решение.

Нельзя незаметно превратить `OPTION` в потребность или в выбранную архитектуру.

### OPEN_QUESTION

Нужно уточнение у пользователя / продукта или более глубокий research.

Продуктовый пробел, без которого нельзя понять потребность или дать оценку → вопрос пользователю.

Техническая неопределённость, которую не закрыл scan → `NEEDS_SOLUTION_RESEARCH`, не выдуманный вариант.

## Что нельзя повышать

| Источник | Не превращать в |
| --- | --- |
| комментарий пользователя | командное решение, requirement, confirmed architecture |
| предложение автора треда | выбранное решение |
| найденный аналог / похожая фича | обязательный способ реализации |
| inference | confirmed fact / `OURS_CONFIRMED` |
| отсутствие данных в ответе tool | «в системе этого нет» |

Не писать `в обсуждении решили`, `команда склонялась`, `было согласовано`, если в источниках этого нет.

## Если уже есть предложенное решение

Не оценивать его первым.

1. Сформулировать потребность без этого решения.
2. Зафиксировать предложенный способ как `OPTION`.
3. На scan проверить, есть ли более простой / естественный путь.
4. Только потом сравнивать плюсы / минусы.

Плохо:

```text
Нужно проверять соответствие segment ↔ SKU на новом сервисе. Оценка: XL.
```

Хорошо:

```text
Потребность: ограничить видимость SKU по сегменту.
Предложено: проверять segment ↔ SKU.
```

Дальше — scan и, если найден более простой путь, показать его до оценки.
