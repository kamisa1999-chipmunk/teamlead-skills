# Feature-assessment

Быстрый входной skill для сырых продуктовых / технических запросов.

Типичный вход: сообщение из Mattermost, screenshot треда, короткое голосовое описание, кусок Jira, ссылка на существующую Story, просьба «прикинь, как это сделать и сколько примерно займёт».

Skill помогает понять:

- что на самом деле просят;
- где заканчивается проблема и начинается предложенное автором решение;
- относится ли запрос к зоне команды пользователя;
- есть ли очевидно более простой технический путь;
- достаточно ли данных для rough estimate;
- нужен ли более глубокий technical research.

Главный принцип:

> Не оценивать предложенное решение автоматически. Сначала отделить потребность от реализации и проверить, есть ли более подходящий способ решить задачу.

Не пишет Story. Не ставит задачу аналитику. Не делает полный architecture research. Не публикует в Jira / Mattermost. Не читать reference-файлы заранее. Каждый — только на своём этапе.

Как выглядит папка фичи, если её уже завели: вымышленный образец `examples/features/items/01-reading-list/` (от этой папки: `../../examples/`). Живые фичи — в `notes/features/`.

## Связка скиллов

| Skill | Ответственность |
| --- | --- |
| **`feature-assessment`** | быстрый разбор сырого запроса / feasibility / ownership / rough estimate |
| `story-prep` | нормальная продуктовая Story |
| `sa-task-prep` | формальная постановка задачи аналитику |
| `solution-research` | глубокая техническая проработка вариантов |
| `sa-review` | review выполненного системного анализа |

`feature-assessment` не должен подменять ни один из них.

После показа assessment не запускать другие скиллы автоматически. Можно предложить следующий шаг: `story-prep`, `sa-task-prep` (если уже есть Story) или `solution-research`.

## Режимы

Определить режим **до** исследования. По умолчанию `quick`.

| id | Когда | Ориентир |
| --- | --- | --- |
| `quick` | обычный входной запрос; «прикинь», «это наша?», скрин треда | 3–5 минут research; не делать глубокий code archaeology; не строить design package |
| `deep` | «подробнее», «deep», «копни перед оценкой» | до ~10 минут; можно пройтись по нескольким репозиториям и аналогам; всё ещё не заменяет `solution-research` |

Если даже `deep` не даёт уверенности для разумной оценки → `NEEDS_SOLUTION_RESEARCH`.

## Инварианты

- предложенное решение не считать правильным только потому, что его предложил автор запроса;
- сначала потребность, потом реализация;
- если найден более простой / естественный путь — показать его **до** оценки;
- не генерировать несколько вариантов ради количества;
- комментарии пользователя имеют высокий приоритет;
- не требовать заранее заполненную карту ответственности и не создавать её;
- не придумывать конкретную owning team без основания;
- если ownership не подтверждён — уточнить у пользователя;
- не делать вид, что skill знает оргструктуру лучше пользователя;
- часть запроса вне зоны пользователя — не тратить на неё глубокий technical research без отдельной причины;
- не исследовать весь Confluence / всю Jira / весь код;
- не задавать вопрос, на который отвечает доступный Jira / Confluence / код;
- не повышать источник информации;
- пользовательский комментарий ≠ командное решение;
- предложение автора треда ≠ выбранное решение;
- найденный аналог ≠ обязательный способ реализации;
- inference ≠ confirmed fact;
- rough estimate — диапазон, не точное число, и не командная оценка;
- оценку давать только при статусе `ESTIMATABLE`;
- confidence только `low` / `medium` / `high`, без процентов;
- не публиковать в Jira и не отправлять сообщение в тред;
- не писать runtime-state в tracked-файлы.

## Provenance

Внутренне различать каждое существенное утверждение. Пользователю не показывать полную разметку без необходимости. Язык ответа должен сохранять уровень уверенности.

| Метка | Что это |
| --- | --- |
| `FACT` | подтверждено источником: Jira, документ, код, явное подтверждение |
| `USER_INPUT` | комментарий / уточнение пользователя этого прогона |
| `ASSUMPTION` | принято для оценки, не подтверждено |
| `INFERENCE` | осторожный вывод из контекста |
| `OPTION` | возможный способ реализации, не выбранное решение |
| `OPEN_QUESTION` | нужно уточнение |

Подробности — в `classification.md` на шаге нормализации.

## Pipeline

Идти по порядку. Внутреннюю модель и лог поиска не показывать.

```text
определить режим
→ исходные материалы              ← прочитать sources.md
→ нормализация запроса            ← прочитать classification.md
→ ownership                       ← прочитать ownership.md
→ быстрый technical scan          ← прочитать research.md
→ оценка предложенного подхода
→ предварительный scope
→ что удешевляет / усложняет
→ вопросы blocking / non-blocking
→ verdict / estimate              ← прочитать output-format.md
→ показ пользователю
→ (если просили) ответ для треда — не отправлять
```

Копировать:

```text
Feature-assessment:
- [ ] Режим: quick | deep
- [ ] Исходные материалы (sources.md)
- [ ] Нормализация: проблема / предложенное решение / ограничения / неизвестное
- [ ] Ownership по каждому подзапросу (ownership.md)
- [ ] Technical scan (research.md)
- [ ] Оценка предложенного подхода; более простой путь — до оценки
- [ ] Предварительный scope
- [ ] Удешевляет / усложняет — только релевантное
- [ ] Вопросы: blocking / non-blocking
- [ ] Verdict
- [ ] (ESTIMATABLE) rough estimate + assumptions + confidence
- [ ] Показ (output-format.md)
- [ ] (опционально) ответ для треда — не отправлять
```

### 1. Режим и исходные материалы

Прочитай `sources.md`. Собрать всё, что дал пользователь: текст, screenshot, ссылку, Jira key, дополнительный комментарий.

Комментарии пользователя имеют высокий приоритет. Пример: «Пункт 2 точно наша зона ответственности, остальные под вопросом» — пункт 2 = `OURS_CONFIRMED`; остальные не назначать другим командам без подтверждения; ownership по контексту можно предположить, но маркировать как гипотезу.

### 2. Нормализация запроса

Прочитай `classification.md`. Отделить:

- **Проблема / потребность** — что хотят получить с точки зрения поведения продукта или системы;
- **Предложенное решение** — если автор запроса уже предложил технический способ;
- **Ограничения / контекст** — что известно из сообщения пользователя, Jira, Confluence или предыдущего контекста;
- **Неизвестное** — что пока неясно.

Предложенное решение не считать правильным только потому, что его предложил автор запроса.

Если запрос состоит из нескольких инициатив — нормализовать каждую отдельно.

### 3. Ownership

Прочитай `ownership.md`. Для каждого подзапроса — один статус: `OURS_CONFIRMED` / `OURS_LIKELY` / `SHARED` / `OTHER_TEAM_LIKELY` / `UNKNOWN`.

Карту ответственности не создавать и не подгружать. Если часть явно не наша — не углублять technical scan без отдельной причины.

### 4. Быстрый technical scan

Прочитай `research.md`. Ограниченное исследование: существующие механизмы, похожие фичи, точки интеграции, reusable компоненты, потенциальные ограничения.

Не делать полный architecture research. Глубина — по режиму `quick` / `deep`.

### 5. Оценка предложенного подхода

Если во входе был предложен способ реализации:

- проверить, насколько он соответствует текущей архитектуре;
- определить основные плюсы / минусы;
- проверить, нет ли более простого варианта;
- при необходимости предложить 1–2 альтернативных направления.

Не генерировать несколько вариантов ради количества.

Если найден более простой / естественный путь — явно показать его **до** оценки.

### 6. Предварительный scope

Предположительно затронутые области: backend, admin, web, iOS, Android, BFF, data / ranking, external service, contracts, documentation.

Каждую релевантную область маркировать: `confirmed` / `likely` / `possible` / `not relevant`.

Не превращать предположение в факт. `not relevant` показывать, только если это снимает ожидание из запроса.

### 7. Что делает задачу дешёвой / дорогой

Короткий блок только из релевантных факторов. Универсальный список автоматически не копировать.

**Упрощает** — существующий reusable механизм; изменение только в одном слое; отсутствие изменений контрактов; backward compatibility без специальных сценариев; существующие аналоги.

**Усложняет** — новый сервис / новая интеграция; изменения на всех клиентах; ranking / ML / персонализация; миграции данных; backward compatibility; shared ownership нескольких команд; отсутствие контрактов / спецификаций; новые product rules.

### 8. Вопросы

Если без ответов нельзя дать разумную оценку — 1–5 коротких вопросов.

- `blocking` — без ответа разумной оценки нет;
- `non-blocking` — оценку (если она возможна) не блокируют, но влияют на уверенность или верхнюю границу.

Не задавать вопросы, на которые можно ответить через доступные Jira / Confluence / код.

### 9. Verdict и показ

Прочитай `output-format.md`. Закончить одним статусом:

| Статус | Когда |
| --- | --- |
| `ESTIMATABLE` | данных достаточно для rough estimate |
| `NEEDS_ANSWERS` | нужны ответы пользователя / продукта |
| `NEEDS_SOLUTION_RESEARCH` | для разумной оценки нужен более глубокий technical research |
| `OTHER_TEAM` | основной scope принадлежит другой команде / вне зоны пользователя |
| `MIXED` | несколько инициатив с разным ownership / readiness |

Rough estimate — только если статус `ESTIMATABLE`. Формат: `S` / `M` / `L` / `XL`, или диапазон в спринтах, если пользователь явно просит спринты. Обязательно assumptions и qualitative confidence.

Не маскировать rough estimate под командную оценку.

## Запреты

Нельзя: принимать предложенное решение как выбранное; назначать чужую команду без основания; делать полный architecture research; писать DeliveryStory или SA Task; запускать `sa-spec` / `sa-review`; выдавать точные часы или проценты уверенности; отправлять сообщение в Mattermost; автоматически менять Jira; писать runtime-state в tracked-файлы.
