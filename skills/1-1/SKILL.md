# 1:1 — заметки по команде

## Расположение

```
notes/teams/{гильдия}/{slug}/README.md    — карточка (оглавление)
notes/teams/{гильдия}/{slug}/1-1.md       — история 1:1 и подготовки
notes/teams/{гильдия}/{slug}/follow-up.md — follow-up и управленческий контур
notes/teams/{гильдия}/{slug}/peers.md     — ОС коллег
notes/teams/{гильдия}/{slug}/meeting-context.md — групповые встречи
notes/teams/{гильдия}/{slug}/observations.md    — наблюдения
notes/teams/{гильдия}/{slug}/hr.md        — HR / ИПР (если есть записи)
notes/leadership/kamilla-saidova.md      — рефлексия тимлида
notes/1-1/                               — этот скилл
```

Структура файлов и шаблон README — `notes/teams/_template.md`.  
Конспекты: обычно `~/Downloads/`, формат `.txt`. Подробности — в [reference.md](reference.md).

**Как найти человека:** `notes/teams/{гильдия}/*/README.md` → поле `Имя` в «Основная информация». Не брать `_template.md`, чек-листы SA и sidecar-файлы без README.

## Общие правила

- **Дописывать, не перезаписывать** — история важна.
- **`1-1.md`:** новые записи (итоги и «Подготовка ДД.ММ.ГГГГ») — **в начало файла**, сразу после заголовка. Свежие сверху, старые ниже. В конец не дописывать. Если подготовка на эту дату уже есть — обновить этот блок на месте, не дублировать.
- **Формат даты в заметках:** `ДД.ММ.ГГГГ`.
- **Стиль:** фактологично, списки через `*`.
- Плейсхолдеры `[заполнить]` — заменять содержимым, не оставлять.
- Пустые поля: `-`.
- Ссылки на Jira: `[CAT2-1234](https://jira01.goldapple.ru/browse/CAT2-1234)`.

## Сценарий 1: Фиксация итогов 1:1 из конспекта

Пользователь **не пишет заметки вручную**. Она присылает файл конспекта встречи (голосом или текстом просит зафиксировать результаты 1:1).

### Вход

- **Файл конспекта** — путь к `.txt` (прикреплённый или указанный).
- **Команда пользователя** — например: «зафиксируй результаты этого 1:1», «запиши итоги ван-вана».

Ручные заметки от пользователя **не обязательны** — всё извлекается из конспекта.

### Шаги

1. **Прочитать конспект** — весь файл.
2. **Определить дату** — из первой строки (`Встреча проходила ДД.ММ.ГГГГ`) или из имени файла.
3. **Определить участника 1:1** — см. [reference.md](reference.md):
   - извлечь спикеров;
   - исключить `Саидова Камилла Зарифовна`;
   - если 1 другой участник → он адресат; иначе — уточнить.
4. **Найти карточку** — каталог `notes/teams/{гильдия}/{slug}/` по имени из конспекта (см. [reference.md](reference.md)).
5. **Прочитать** `README.md` и `1-1.md` (при необходимости `follow-up.md`, `hr.md`).
6. **Извлечь из конспекта** рабочее содержание:
   - темы обсуждения;
   - обратная связь (что сказал человек, что сказала тимлид);
   - блокеры;
   - договорённости и action items.
   - Пропустить small talk и личные отступления.
7. **Добавить запись** в **начало** `1-1.md` (после заголовка, свежие сверху) по шаблону ниже.
8. **Обновить смежные файлы**, если следует из содержания:
   - `README.md` → открытые договорённости, развитие и мотивация, дата последнего 1:1
   - `observations.md` — только через скилл `observations`, с валидацией
9. **Peer feedback о коллегах** — если в конспекте обсуждали работу других людей из команды (см. ниже).
9б. **Action items тимлида** — прочитать скилл `action-items`, сценарий 2 на том же конспекте; зафиксировать обязательства Камиллы в `notes/leadership/kamilla-saidova.md` → `## Мои action items`. Неясные сроки — вопросы в резюме или уточнение одним блоком.
10. **Показать резюме:** кто, дата, что добавлено, куда (включая файлы коллег, если обновлялись); строка **«Мои action items: …»**.
11. **Предложить разбор** (сценарий 1б):

> Итоги зафиксированы. Хочешь разобрать встречу в коучинговом формате — твои мысли, наблюдения и как ты себя вела?

Если **да** → сценарий 1б. Если **нет** или молчание — завершить.

Если нужно зафиксировать follow-up по договорённостям, можно предложить продолжение:

> Если хочешь, я ещё могу подготовить follow-up: мягкий текст письма сотруднику и отдельно фактологичную запись по договорённостям в твою приватную секцию.

### Peer feedback о коллегах (шаг 9)

Если на 1:1 собеседник давал **обратную связь о других людях** (peer feedback, оценка работы коллег, сравнения) — зафиксировать **в файле каждого упомянутого коллеги**, не только у участника 1:1.

**Куда:** `notes/teams/{гильдия}/{slug}/peers.md`  
Если файла нет — создать по шаблону из `notes/teams/_template.md`.

**Формат записи:**

```markdown
* От [Имя Фамилия собеседника] (1:1 ДД.ММ.ГГГГ, peer feedback) — [краткая суть одной строкой]
  * [факт / цитата по смыслу из конспекта]
  * [ещё факт, если есть]
```

**Правила:**

| | |
|---|---|
| **В файле коллеги** | Только то, что **сказал собеседник 1:1** — с атрибуцией «От Насти…», «От Андрея…» |
| **В файле участника 1:1** | Краткое упоминание в `**Темы:**` или `**Обратная связь:**` — кого обсуждали, без полного дублирования |
| **Не путать с наблюдениями** | В `observations.md` коллеги peer feedback **не** класть — туда идут наблюдения тимлида (→ скилл `observations`, с валидацией) |
| **Нет кейсов** | Если собеседник дал общую оценку без примеров задач — явно указать: `Конкретных кейсов на встрече не привёл` |
| **Чувствительное** | Решения тимлида об увольнении, домыслы, ярлыки — **не** писать в файлы коллег; только факты из конспекта |

**Определение коллег:** по имени/фамилии из конспекта → файл в `notes/teams/` (см. [reference.md](reference.md)). Если человек не из команды или файл не найден — упомянуть в резюме, не выдумывать.

**В резюме после фиксации** перечислить: «ОС коллег обновлена: Маша, Руслан, …» или «peer feedback в конспекте не было».

### Шаблон записи 1:1

Дата — отдельной строкой (без `###`), в **начало** `1-1.md` (сразу после заголовка «# 1:1 — …» и строки про порядок записей). Старые записи не двигать и не удалять.

```markdown

ДД.ММ.ГГГГ
  * **Темы:**
    * [тема]
  * **Сложности / блокеры:** [блокеры или `-`]
  * **Обратная связь:**
    * [содержание]
  * **Договорённости:**
    * [договорённость]
  * **Action items:**
    * [действие]
```

### Чего не делать

- Не удалять и не переписывать старые записи.
- Не добавлять новые 1:1 или подготовки в **конец** `1-1.md` — только в начало (или обновить существующую подготовку на ту же дату).
- Не менять `onboarding.md` и цели без явной просьбы.
- Не выдумывать факты — только то, что есть в конспекте.
- Не включать small talk в итоговую запись.
- Не дублировать полный peer feedback только в файл участника 1:1 — он живёт в `peers.md` у каждого коллеги.
- Не записывать peer feedback в `observations.md` без валидации тимлида.

## Сценарий 1б: Разбор и коучинг после 1:1

После фиксации итогов (сценарий 1) или по отдельной команде. Цель — **не только записать факты встречи**, но помочь тимлиду осмыслить её: мысли, интерпретации, наблюдения о человеке и **о своём поведении** на 1:1.

### Вход

- Конспект `.txt` (тот же, что для фиксации, или новый).
- Команды: «разбери 1:1», «коучинг после ван-вана», «как я провела 1:1», «рефлексия после встречи с Димой».
- Если сценарий 1 уже выполнен — использовать уже прочитанный конспект и файл человека.

### Принципы

- **Тон:** коуч, не судья. Эмоции и сомнения тимлида — нормальны.
- **Два контура:** (A) про человека и ситуацию, (B) про поведение тимлида на встрече.
- **В файл сотрудника** — только факты (итоги 1:1, наблюдения после валидации). **Интерпретации тимлида** — в `notes/leadership/kamilla-saidova.md` или только в чате.
- **Не допрашивать** — 2–4 вопроса за раунд, итеративно.
- **Не выдумывать** анализ поведения тимлида — опираться на конспект (реплики, длина, вопросы).

### Фаза R1 — Рефлексия: твои мысли

Сначала кратко напомнить: с кем 1:1, дата, 2–3 факта из только что зафиксированных итогов.

Задать **2–4 вопроса** (выбрать по ситуации):

- Что больше всего запомнилось после встречи?
- Что тебя удивило или насторожило?
- Как ты сейчас оцениваешь ситуацию с этим человеком — что думаешь?
- Что хотелось сказать, но не сказала?
- Как думаешь, что он/она вынес(ла) из встречи?
- Есть ли что-то, что тебя беспокоит после разговора?

**После ответа** — отразить услышанное (1–2 предложения) и задать уточнение, если ответ общий или эмоциональный:

- «Когда ты говоришь „напряжённо“ — что именно было напряжённым?»
- «Это первый раз или уже повторяется?»

Повторять раунды, пока картина не прояснится, или тимлид не скажет «достаточно».

### Фаза R2 — Наблюдения о человеке (опционально)

Если из рефлексии всплывают **наблюдения о сотруднике**, которые стоит сохранить:

1. **Не записывать сразу** — применить правила валидации из скилла `observations` (факт / интерпретация / эмоция).
2. Итеративно довести до фактологичной формулировки.
3. Предложить черновик строки в `observations.md`.
4. Записать **только после подтверждения** («да», «записываем»).

Если тимлид не хочет фиксировать — оставить в рефлексии для `leadership`-файла или только в чате.

### Фаза R3 — Анализ твоего поведения на 1:1

На основе **конспекта** (реплики `Саидова Камилла Зарифовна`) — короткий разбор. Показать явно, что это гипотезы для обсуждения, не приговор.

```markdown
## Как ты вела 1:1 — ДД.ММ.ГГГГ, [Имя]

### Что вижу в конспекте
- **Баланс:** [примерно кто сколько говорил — качественно, не проценты из головы]
- **Вопросы:** [открытые / закрытые; уточняющие / наводящие — с примерами из текста]
- **Обратная связь:** [дала / смягчила / отложила / не прозвучала — с опорой на реплики]
- **Договорённости:** [чёткие action items / размытые / не зафиксированы]
- **Связь с прошлым:** [вернулась к старым темам / нет — если видно из контекста файла]

### Возможные зоны внимания
- [1–3 пункта — мягко, в стиле «можно обратить внимание»]

### Что сработало хорошо
- [1–2 пункта — обязательно, если есть]
```

**Критерии анализа** (не все обязательны — по релевантности):

| Сигнал | На что смотреть |
|--------|-----------------|
| Много говорила сама | Длинные монологи тимлида, мало вопросов человеку |
| Решала за человека | Предложения вместо «что ты думаешь?» |
| Избегала сложной ОС | Уход от темы, смягчители, смена subject |
| Хороший коучинг | Открытые вопросы, пауза, переспрашивание, резюме |
| Структура | Была ли повестка, закрыли ли action items |
| Эмоции | Защита, оправдания, раздражение в репликах тимлида |

Спросить: **«Откликается? Что поправить или добавить?»**

### Фаза R4 — Коучинговые рекомендации

2–4 рекомендации **для тимлида** на следующие встречи с этим человеком (или в целом):

```markdown
## Рекомендации для тебя

1. **[Фокус]** — [конкретное действие на следующий 1:1]
   Зачем: [связь с тем, что обсудили]
2. …
```

Типы рекомендаций:
- больше слушать / меньше советовать;
- вернуться к незакрытой теме;
- дать более прямую ОС (или наоборот — смягчить);
- проверить договорённость до встречи;
- подготовить один конкретный вопрос;
- не тащить в 1:1 то, что лучше в другом формате.

Спросить: **«Что из этого берёшь? Что не откликается?»**

### Фаза R5 — Сохранение (опционально)

Спросить:

> Сохранить разбор в `notes/leadership/kamilla-saidova.md`? (да / нет / только в чате)

Если **да** — дописать блок в `## Разбор 1:1` по шаблону из `leadership/kamilla-saidova.md`:

- **Мои мысли** — из R1 (можно интерпретации)
- **Что заметила в своём поведении** — из R3 + ответы тимлида
- **Коучинговые заметки** — из R4 (подтверждённые)
- **На следующий 1:1** — 1–3 пункта action items для тимлида

**Не сохранять** без явного согласия.

### Чего не делать

- Не писать интерпретации тимлида в файл сотрудника.
- Не записывать наблюдения без валидации (→ `observations`).
- Не критиковать тимлида жёстко — формулировки «можно попробовать», «зона внимания».
- Не анализировать поведение сотрудника в R3 — только тимлида.
- Не выдавать один длинный опросник — итеративный диалог.
- Не диагностировать личность ни сотрудника, ни тимлида.

## Сценарий 1в: Follow-up по договорённостям

Этот сценарий нужен, когда после 1:1 надо:

1. Подготовить **общий follow-up текст** для письма сотруднику и тимлиду — в одном из двух режимов.
2. Отдельно зафиксировать **приватную фактологичную историю** договорённостей, сроков и срывов в файле сотрудника.

Это **не скрытый HR-документ** и не текст «про увольнение». Здесь два осознанно разных контура:

- **общий контур** — прозрачная фиксация договорённостей для сотрудника;
- **приватный контур** — история управленческих фактов для тимлида.

Общий follow-up может использоваться как часть документирования ожиданий, но **не заменяет** формальные HR-процедуры при эскалации.

### Когда использовать

Триггеры:

- «сделай follow-up по 1:1»
- «подготовь письмо по договорённостям»
- «официальный follow-up»
- «мягкий follow-up»
- «зафиксируй невыполненные договорённости»
- «собери follow-up после разговора с [имя]»

### Два режима общего письма

| Режим | Когда использовать | Тон |
|-------|-------------------|-----|
| **Мягкий** | первая фиксация после 1:1; нет срыва; обычная синхронизация | короткий, дружелюбный, без давления |
| **Официальный** | повторное обсуждение; невыполненная договорённость; накопление фактуры; пользователь явно просит официальный follow-up | деловой, структурированный, явный |

**По умолчанию:**
- если срыва нет и это первая фиксация → **мягкий**;
- если договорённость не выполнена, обсуждали повторно или пользователь просит фиксацию для эскалации → **официальный**.

Если режим неочевиден — спросить:

> Какой режим письма нужен: **мягкий** (обычная синхронизация) или **официальный** (явная фиксация с историей и подтверждением)?

### Вход

- Конспект `.txt` или уже зафиксированные итоги 1:1 в файле человека.
- Имя сотрудника, если неочевидно.
- Режим письма: `мягкий` / `официальный` (если не указан — выбрать по правилам выше).
- При необходимости — текущий статус договорённостей от пользователя:
  - что выполнено;
  - что не выполнено;
  - что перенесено;
  - что обсуждали повторно.

Если по конспекту или заметкам **нельзя надёжно понять статус**, спросить коротко и предметно, а не придумывать.

### Выход

#### Выход A — общий текст письма

Подготовить черновик письма/сообщения сотруднику и тимлиду по шаблону выбранного режима.

#### Выход B — приватная запись для тимлида

В том же файле сотрудника, в отдельной секции, дописать запись для истории follow-up — включая режим письма, факт отправки и ответ сотрудника (если известен).

### Принципы

- **Факты отдельно от интерпретаций.**
- **В мягком письме** — только текущие договорённости; без истории срывов.
- **В официальном письме** — явная хронология по проблемным пунктам: когда договорились, какой был срок, что не закрыто, что договорились сейчас.
- **В приватную секцию** — только проверяемые факты:
  - что было обещано;
  - какой был срок;
  - что фактически произошло;
  - когда это повторно обсуждали;
  - на чём договорились дальше;
  - какое письмо отправлено и был ли ответ.
- Не писать в приватной секции:
  - ярлыки;
  - диагнозы;
  - предположения о мотивах;
  - формулировки про увольнение, санкции, «копим кейсы».

### Шаги

1. Определить сотрудника и прочитать `README.md` + `1-1.md` + `follow-up.md` в его каталоге `notes/teams/{гильдия}/{slug}/`.
2. Найти последнюю релевантную запись 1:1 и/или follow-up по этой теме.
3. Извлечь договорённости:
   - задача / обязательство;
   - срок;
   - ожидаемый результат (измеримый, если возможно);
   - кто владелец.
4. Определить текущий статус:
   - `выполнено`
   - `частично`
   - `не выполнено`
   - `перенесено`
   - `в работе`
5. Выбрать режим письма (`мягкий` / `официальный`) или уточнить у пользователя.
6. Если статус неочевиден из материалов — уточнить у пользователя.
7. Сформировать **общий follow-up текст** по шаблону режима.
8. Дописать **приватную запись** в файл сотрудника.
9. Кратко показать пользователю:
   - какой режим выбран и почему;
   - что вошло в письмо;
   - что зафиксировано в приватной части;
   - какой файл обновлён.
10. После отправки письма пользователь может попросить обновить приватную запись: дата отправки, ответ сотрудника или отсутствие ответа.

### Приватная запись в файле сотрудника

Писать в `follow-up.md`. Если файла нет — создать по шаблону из `notes/teams/_template.md`.

Файл предназначен **только для тимлида**. Агент не должен использовать его как источник формулировок для общего письма слово в слово.

### Шаблон приватной записи

Запись добавлять в конец секции:

```markdown

ДД.ММ.ГГГГ
  * **Контекст:** [после какого 1:1 / какого follow-up]
  * **Режим письма:** [мягкий / официальный]
  * **Договорённость:**
    * [что именно должен был сделать сотрудник]
  * **Срок:** [дата / период / `-`]
  * **Статус:** [выполнено / частично / не выполнено / перенесено / в работе]
  * **Факт по статусу:**
    * [что произошло фактически, без интерпретаций]
  * **Обсуждали повторно:**
    * [когда и что проговорили] / `-`
  * **Следующий шаг / новая договорённость:**
    * [что договорились сделать дальше]
  * **Письмо:**
    * тема: [тема письма]
    * отправлено: [дата] / `[заполнить после отправки]`
  * **Ответ сотрудника:**
    * [текст ответа / возражения / `-`] / `ответа не было`
  * **Согласие по умолчанию:**
    * [если в официальном письме был блок про отсутствие возражений — дата, с которой договорённости считаются принятыми] / `-`
```

### Правила приватной записи

- Формулировать так, чтобы через несколько месяцев было понятно:
  - что обещали;
  - к какому сроку;
  - что произошло;
  - как менеджер на это отреагировал;
  - что было следующим шагом;
  - какое письмо ушло и был ли ответ.
- Если договорённость повторяется из раза в раз — не сливать всё в одну строку, а вести историю по датам.
- Если сотрудник предупредил о риске заранее, это тоже фиксировать как факт.
- Если срок не называли, писать `-`, а не выдумывать.
- Если есть повторный срыв, прямо писать факт:
  - `к 12.07 статус не прислал`
  - `обещанный документ к встрече не подготовил`
  - `на повторном обсуждении 19.07 сообщил, что не возвращался к задаче`
- Если сотрудник ответил с возражениями — фиксировать суть возражений, не переписывая их как согласие.
- Если ответа не было в срок из официального письма — фиксировать `ответа не было` и дату, с которой договорённости считаются принятыми по умолчанию.

### Шаблон мягкого follow-up письма

Тон: спокойный, рабочий, без давления. Цель — синхронизировать ожидания и следующий шаг.

```markdown
Тема: Follow-up по 1:1 от ДД.ММ.ГГГГ

Привет!

Спасибо за встречу. Коротко зафиксирую, о чём договорились:

* [договорённость 1]
* [договорённость 2]

Что ожидаем по срокам:

* до ДД.ММ — [измеримый результат / статус]
* до ДД.ММ — [измеримый результат / статус]

Если по ходу появится риск или сдвиг по срокам — дай, пожалуйста, статус заранее.
```

**Мягкий режим не использует** блок про согласие по умолчанию и не включает историю невыполненных договорённостей.

### Шаблон официального follow-up письма

Тон: деловой, структурированный, явный. Цель — зафиксировать договорённости, хронологию по проблемным пунктам и получить подтверждение (явное или по умолчанию).

```markdown
Тема: Follow-up по договорённостям после 1:1 от ДД.ММ.ГГГГ

Добрый день!

Фиксирую итоги нашего разговора и договорённости.

**По пункту: [название темы / задачи]**

1. Ранее, по итогам 1:1 от ДД.ММ.ГГГГ, мы договорились, что [сотрудник] [конкретное действие] до ДД.ММ.ГГГГ.
2. На встрече ДД.ММ.ГГГГ мы вернулись к этому пункту. На тот момент [факт: пункт не был закрыт / материалы не были предоставлены / статус не был прислан].
3. Мы повторно договорились, что [сотрудник] [конкретное действие] до ДД.ММ.ГГГГ.

**Ожидаемый результат:**
* [измеримый результат 1]
* [измеримый результат 2]
* срок: до ДД.ММ.ГГГГ

**По остальным договорённостям:**
* [договорённость] — срок: до ДД.ММ.ГГГГ

Если видишь риск срыва срока или нужна помощь, пожалуйста, сообщи заранее.

Прошу подтвердить получение письма. Если у тебя есть замечания или возражения по зафиксированным договорённостям — напиши в ответ в течение 2 рабочих дней. При отсутствии возражений в этот срок договорённости, указанные в письме, считаем принятыми.
```

### Правила для официального письма

- Использовать **«Добрый день»**, не «Привет».
- По каждому проблемному пункту — **нумерованная хронология**: когда договорились → что не закрыто → что договорились сейчас.
- **Ожидаемый результат** — измеримый: не «закрыть вопрос», а «прислать список peer feedback от 3 коллег + краткий summary».
- Формулировать факты нейтрально, но **явно**:
  - `материалы не были предоставлены`
  - `пункт не был закрыт к согласованному сроку`
  - `статус не был прислан`
- Не писать:
  - приватные управленческие оценки;
  - намёки на увольнение или санкции;
  - формулировки вроде «ты не справляешься», если это не было прямой обратной связью на встрече.

### Блок согласия по умолчанию (только официальный режим)

В конце официального письма **обязательно** включать:

```markdown
Прошу подтвердить получение письма. Если у тебя есть замечания или возражения по зафиксированным договорённостям — напиши в ответ в течение 2 рабочих дней. При отсутствии возражений в этот срок договорённости, указанные в письме, считаем принятыми.
```

Правила:

- Срок по умолчанию: **2 рабочих дня** с момента отправки, если пользователь не указал иной.
- Формулировка относится **только к зафиксированным в письме договорённостям**, не к «согласию на увольнение» или иным HR-решениям.
- Если сотрудник ответил с возражениями — это **не** согласие; фиксировать возражения в приватной записи.
- После истечения срока без ответа — в приватной записи указать дату, с которой договорённости считаются принятыми по умолчанию.

### Правила для мягкого письма

- Писать так, чтобы сотруднику было ясно:
  - что именно ожидается;
  - к какому сроку;
  - когда дать статус.
- Не включать историю прошлых срывов.
- Не включать блок согласия по умолчанию.
- Не писать приватные управленческие оценки и намёки на санкции.

### Как выбирать тон

| Контур | Режим | Тон | Что включать |
|--------|-------|-----|--------------|
| **Письмо сотруднику** | мягкий | короткий, дружелюбный | текущие договорённости, сроки, next step |
| **Письмо сотруднику** | официальный | деловой, явный | хронология по проблемным пунктам, измеримые результаты, подтверждение / согласие по умолчанию |
| **Приватная секция** | любой | формальный, по датам и фактам | история обещаний, статусы, письмо, ответ, согласие по умолчанию |

### Чего не делать

- Не смешивать мягкий и официальный шаблоны в одном письме.
- Не вставлять в письмо фразы из приватной секции дословно, если они звучат жёстко.
- Не использовать приватную секцию для эмоций тимлида.
- Не писать «не выполняет системно», если в записи нет фактов по датам.
- Не трактовать неоднозначность в худшую сторону — при нехватке данных уточнять у пользователя.
- Не использовать блок «согласие по умолчанию» в мягком режиме.
- Не записывать «согласие по умолчанию» в приватной части, пока не истёк срок и нет подтверждения от пользователя, что ответа не было.

## Сценарий 2: Подготовка к 1:1

Интерактивный сценарий: читать заметки, вести диалог, **сохранить повестку в файл** для подглядывания на встрече.

Опционально подключает **краткий** контекст из скилла `jira-employee-analysis` (отчёты в `notes/jira/reports/employees/`). Jira-анализ остаётся самостоятельным скиллом: полный отчёт не копировать в карточку, CLI не запускать без подтверждения.

### Вход

- Имя человека (или путь к файлу).
- Команда: «подготовься к 1:1 с Димой», «нужна подготовка к ван-вану с…».

### Фаза A — Сводка и анализ человека

1. Найти каталог человека в `notes/teams/{гильдия}/{slug}/`, прочитать `README.md`. Если статус не «в команде» — не готовить 1:1, сказать об этом.
2. Прочитать `meeting-context.md` за период **с даты последнего состоявшегося 1:1** (см. A0). Более ранние блоки — только если нужен кейс для ОС, которого нет в `observations.md`. См. [reference.md](reference.md).
3. **Jira-период и отчёт** — см. A0j ниже (предложить / подключить до или вместе со сводкой; без автозапуска CLI).
4. Выдать части A0 → A0j (если есть) → A1 → A2.

#### A0. Контекст с других встреч (если есть)

Кратко: что человек говорил/делал на групповых встречах с прошлого 1:1.  
Источник — `meeting-context.md` (наполняется скиллом `meeting-context`). Читать блоки **с даты последнего 1:1**. Файл копится целиком — не просить «почистить старое» ради краткости; старое нужно для кейсов ОС.

Если файла нет, он пустой или за период нет блоков — пропустить, не сканировать Downloads в этом сценарии.

#### A0j. Контекст из Jira (опционально)

**Период анализа:**

1. Найти дату **последнего состоявшегося** 1:1 в `1-1.md` (и строку «Последняя встреча» в `README.md`): среди записей с итогами (`**Темы:**`, не `Подготовка …`) взять **максимальную календарную дату**, не «первую/последнюю в файле». Блоки `Подготовка ДД.ММ.ГГГГ` и черновики повестки **не считаются** состоявшимся 1:1.
2. Период: **от этой даты до сегодня** (дата из user_info / текущая).
3. Если состоявшегося 1:1 нет — период = **последние два месяца**.

**Идентификация в Jira:**

- Взять `Jira username` / `Jira account id` из таблицы «Основная информация», если заполнены.
- Если пусто — резолвить по имени через скилл `jira-employee-analysis` (CLI / `people_aliases`). Не выдумывать username.
- Если в `README.md` полей ещё нет — при удобном случае добавить пустые строки `Jira username` / `Jira account id` (остальные файлы не трогать). Заполнить username только если пользователь подтвердила или он однозначно известен из отчёта.

**Поиск отчёта:**

- Каталог: `notes/jira/reports/employees/{username}/` (или slug из отчёта).
- Подходящий = JSON, чей `period.start`/`period.end` **покрывает** выбранный период (± несколько дней допустимо) или совпадает по `--from/--to` / label.
- Если подходящего нет, но есть отчёт за другой период — **не подменять молча**: сказать, какой есть, и предложить собрать за нужный.

**Подключение (без автозапуска):**

| Ситуация | Действие |
|----------|----------|
| Есть подходящий отчёт | Прочитать JSON; вставить блок «Контекст из Jira» (ниже) |
| Нет / период не совпадает | Предложить сформировать через `jira-employee-analysis` за вычисленный период. **Ждать подтверждения** |
| Пользователь отказалась | Продолжить подготовку без Jira-блока |
| Пользователь согласилась | Следовать скиллу `jira-employee-analysis` (CLI → новый файл в `reports/employees/`), затем блок |

**Разработчики и MR:**

- Если в отчёте `employee.is_developer == true` и `git_offer.show == true` — **предложить** MR/Git-анализ текстом из `git_offer` (как в `jira-employee-analysis`).
- Не запускать `--with-git` без явного «да».
- Если выполнен — добавить отдельный блок «Контекст из MR / ревью» (кратко: замечания, циклы, паттерны ревью) — без копирования полного git-отчёта.

**Шаблон блока в чате (и при желании — краткий якорь в повестке):**

```markdown
### Контекст из Jira

**Период:** ДД.ММ.ГГГГ — ДД.ММ.ГГГГ  
**Отчёт:** `notes/jira/reports/employees/{user}/{file}.json`

#### Факты
- основные направления работы: …
- завершённые / незавершённые: N / M
- значимые задачи: [CAT2-…](url) — …
- возвраты и долгие этапы: … / нет
- кейсы к разбору: [CAT2-…](url) — [причина из review_cases]

#### Гипотезы (не факты)
- [паттерн из patterns[] или осторожная гипотеза — только если есть несколько задач]

#### Вопросы для обсуждения
- [1–3 вопроса человеку по кейсам/направлениям]
```

Правила блока:

- Источник — только JSON/MD отчёта. Полный отчёт **не** копировать.
- Разделять **факты / гипотезы / вопросы**.
- **Не** делать выводов о квалификации или эффективности только по Jira.
- Повторяющийся паттерн можно **предложить** зафиксировать как наблюдение (→ `observations`), но **не** сохранять автоматически.

#### A1. Фактическая сводка

```markdown
## Сводка: [Имя] — подготовка к 1:1

**Последний 1:1:** [дата] — [1–2 предложения]
**Профиль:** [роль, испытательный срок / важные даты]

### Открытые договорённости
- [дата] — [суть] — [статус]

### Action items (незакрытые)
- [кто] — [что]

### Обратная связь (последняя)
- **От тимлида:** …
- **От человека:** …

### Наблюдения и риски
- [дата, тип] — [суть]

### Развитие и мотивация
- [ключевые пункты или «не заполнено»]

### Цели (если актуально)
- [цели на ИС / полугодие]
```

Правила: данные **только из файла**; пустые плейсхолдеры не включать; просроченные follow-up помечать ⚠️.

#### A2. Анализ для развития

На основе всего файла (1:1, наблюдения, цели, мотивация) — **самостоятельный анализ**, не только пересказ:

```markdown
## Анализ: [Имя]

### Сильные стороны
- [паттерн + откуда в заметках]

### Зоны роста
- [паттерн + откуда в заметках]

### Чем живёт / что мотивирует
- [вывод из «Развитие и мотивация» и 1:1]

### Что может демотивировать
- [если есть сигналы]

### Динамика
- [как менялся человек между 1:1 — что улучшилось, что повторяется]

### Пробелы в понимании
- [чего не хватает в заметках — что стоит узнать на этом 1:1]
```

Учитывать **A0** (контекст с других встреч) и **A0j** (факты Jira), если есть.

Анализ — интерпретация, но **опираться на факты из файла** (и отдельно помечать, что пришло из Jira). Не диагностировать, не ярлыки — наблюдаемые паттерны. Jira не использовать как единственный источник выводов об эффективности.

### Фаза B — Рекомендации: темы и вопросы

На основе сводки и анализа предложить **3–6 рекомендаций** (не больше — уложиться в 30 минут) — пронумерованный список:

```markdown
## Рекомендации к 1:1

1. **[Тема]** (~N мин)
   Зачем: [связь с развитием / риском / целью / договорённостью]
   Вопрос: «[конкретный вопрос человеку]»
   Приоритет: [главная / обычная / быстрая]
```

**Таймбоксинг — 30 минут на всю встречу:**

| Тип темы | Время | Когда использовать |
|----------|-------|-------------------|
| Главная | 10–15 мин | Одна на встречу — центр разговора |
| Средняя | 5–7 мин | Договорённости, ОС, цели |
| Быстрая | 2–3 мин | Чек-ин, уточнение, один вопрос |

Правила планирования:
- **Всего: 30 мин.** Резерв: ~3 мин чек-ин + ~2 мин итоги/action items → **~25 мин на содержание**.
- Если есть **главная тема** — максимум 1–2 средних или быстрых вокруг неё. Не набивать вопросами.
- Если **главной темы нет** — до 4–5 быстрых тем, суммарно ≤25 мин.
- Каждая рекомендация — с оценкой времени и приоритетом.
- При выборе пользователем следить, чтобы сумма **да** ≤ 25 мин; если больше — предложить что отложить.

Типы рекомендаций (миксовать по ситуации):
- закрыть старую договорённость;
- проверить прогресс по зоне роста;
- углубить понимание мотивации;
- дать или уточнить обратную связь;
- обсудить цели (ИС / полугодие);
- закрыть пробел из «Пробелы в понимании»;
- проверить, изменилось ли повторяющееся поведение (риски);
- обсудить кейс/направление из блока Jira (если подключён) — как факт работы, не как оценку человека.

**Спросить пользователя:**

> По каждому пункту: **да** (обсудим) / **нет** (не сейчас) / **знаю** (уже в курсе).
> Можно ответить списком: `1 да, 2 нет, 3 знаю, 4 да…`
> Или добавить свои темы.

Дождаться ответа. В итоговую повестку попадают только пункты с **да** + темы, которые пользователь добавила сама.

### Фаза C — Сбор контекста (интерактивно)

После выбора тем — **два блока вопросов**:

**Блок 1 — что произошло с прошлого 1:1:**
1. Что заметила по человеку с прошлого 1:1?
2. Статус договорённостей и action items?
3. Новые наблюдения, которых ещё нет в заметках?

**Блок 2 — твои цели:**
4. Что для тебя главное на этом 1:1?
5. Какую обратную связь хочешь дать?
6. Есть ли темы, которые человек сам просил обсудить?

Короткий ответ — один уточняющий вопрос, не допрашивать.

### Фаза D — Повестка и сохранение в файл

После ответов пользователя:

1. Собрать повестку: **подтверждённые рекомендации** + **ответы из фазы C**.
2. **Расставить тайминг** — сумма ровно **30 мин**.
3. **Сохранить** в **начало** `1-1.md` (после заголовка). Обновить в `README.md` строку «Последняя встреча», если дата известна.
4. Показать резюме: что сохранено, общее время.

**Дата встречи:** спросить, если не указана. Если пользователь сказала «завтра» — вычислить из текущей даты. Формат: `ДД.ММ.ГГГГ`.

**Заголовок записи** — отдельной строкой (без `###`):

```
Подготовка ДД.ММ.ГГГГ
```

Если подготовка на эту дату уже есть — **обновить её на месте**, не дублировать и не переносить. Если блока ещё нет — вставить **в начало** файла (после заголовка).

**Что сохранять из Jira:** только выбранные пользователем темы встречи и **короткие ссылки** на значимые задачи (если темы из Jira подтверждены). Полный Jira-/MR-анализ остаётся в `notes/jira/reports/employees/` — в карточку не копировать.

**Шаблон записи в файле:**

```markdown

Подготовка ДД.ММ.ГГГГ
  * **План (30 мин):**
    * 3 мин — чек-ин
    * N мин — [главная тема, если есть]
    * N мин — [тема]
    * 2 мин — итоги и action items
  * **Проверить / закрыть:**
    * [пункт]
  * **Обсудить:**
    * [тема]
  * **Обратная связь:**
    * [что дать — позитив / корректирующая]
  * **Вопросы человеку:**
    * [вопрос]
  * **Мои цели на встречу:**
    * [цель]
  * **Контекст с прошлого 1:1:**
    * [из ответов фазы C]
  * **Jira (якоря):**
    * [CAT2-1234](url) — [зачем в повестке]
    * отчёт: `jira/reports/employees/{user}/{file}.json` (не копировать)
  * **Рекомендации (подтверждены):**
    * [тема] (~N мин) — «[вопрос]»
```

Пункт `**Jira (якоря):**` — только если пользователь подтвердила темы из Jira; иначе опустить.

После встречи сценарий 1 **добавляет в начало файла** запись `ДД.ММ.ГГГГ` с итогами. Подготовка на ту же дату остаётся ниже по файлу — не переносить её вручную.

**В чате** показать ту же повестку в удобном для чтения виде (можно с чекбоксами `- [ ]`).

### Чего не делать

- Не удалять старые записи 1:1 и подготовки.
- Не дописывать подготовку в конец `1-1.md`.
- Не включать в повестку рекомендации, которые пользователь отклонил.
- Не превышать **30 минут** в плане; если тем много — предложить отложить.
- Не задавать все вопросы одним списком из 10+ пунктов.
- Не выдумывать факты в сводке; в анализе — только обоснованные выводы из заметок.
- Не перезаписывать итоги прошлых встреч.
- Не запускать `jira-employee-analysis` / `--with-git` без подтверждения пользователя.
- Не копировать полный Jira-/MR-отчёт в карточку сотрудника.
- Не делать выводов о квалификации или эффективности только по Jira.
