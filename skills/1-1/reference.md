# Справочник — скилл 1:1

## Формат конспекта встречи

Файлы конспектов — `.txt`, обычно в `~/Downloads/`.

**Имя файла:** `YYYY-MM-DD HHMM (MSK) {id}.txt`  
Пример: `2026-07-03 0959 (MSK) 0108750527.txt`

**Первая строка — дата встречи:**
```
Встреча проходила 03.07.2026 с 09:59 (MSK). В расшифровке могут быть неточности — проверяйте важное.
```

**Участники** — строки вида:
```
Гуминиченко Дмитрий Александрович:
Саидова Камилла Зарифовна (голос 1):
Кафанова Мария Александровна:
```

**Реплики:**
```
[00:00:15] Текст реплики.
```

## Архитектура скиллов 1:1

| Этап | Скилл | Куда пишет |
|------|-------|------------|
| Подготовка | 1-1 сценарий 2 | `{slug}/1-1.md` → в начало: `Подготовка ДД.ММ.ГГГГ` |
| Jira-факты к подготовке | `jira-employee-analysis` (по подтверждению) | `notes/jira/reports/employees/` — в карточку не копировать |
| Итоги встречи | 1-1 сценарий 1 | `{slug}/1-1.md` → в начало: `ДД.ММ.ГГГГ` |
| Разбор и коучинг | 1-1 сценарий 1б | `leadership/kamilla-saidova.md` (с согласия) |
| Follow-up по договорённостям | 1-1 сценарий 1в | мягкий или официальный текст письма + `{slug}/follow-up.md` |
| Наблюдения о сотруднике | `observations` | `{slug}/observations.md` |
| Peer feedback | 1-1 сценарий 1 | `{slug}/peers.md` у каждого упомянутого коллеги |
| Групповые встречи | `meeting-context` | `{slug}/meeting-context.md` (копится) |

## Определение 1:1

1. Извлечь уникальных спикеров (строки, заканчивающиеся на `:`).
2. Исключить: `Саидова Камилла Зарифовна` (тимлид, владелец конспектов).
3. Если **ровно 1** другой участник → это 1:1, он — адресат заметки.
4. Если участников больше → это не 1:1; уточнить у пользователя.
5. Дата — из первой строки файла (приоритет) или из имени файла.

## Что извлекать из конспекта

**Включать:**
- рабочие темы и обсуждения;
- обратную связь (от человека и от тимлида);
- блокеры и сложности;
- договорённости и action items;
- ответы на подготовленные вопросы 1:1.

**Не включать:**
- small talk (погода, выходные, личные истории тимлида);
- технические артефакты расшифровки («голос 1», таймкоды в итоговой записи).

## Что извлекать для follow-up по договорённостям

Для сценария `1в` дополнительно извлекать:

- исходную договорённость;
- обещанный срок;
- ожидаемый результат;
- статус на сегодня (`выполнено` / `частично` / `не выполнено` / `перенесено` / `в работе`);
- что именно произошло фактически;
- было ли повторное обсуждение;
- новый следующий шаг.

Если статус не виден из конспекта или заметок, его нужно уточнить у пользователя.

## Режимы follow-up письма

| Режим | Когда | Особенности |
|-------|-------|-------------|
| **Мягкий** | первая фиксация, нет срыва | короткий тон, без истории срывов, без блока согласия по умолчанию |
| **Официальный** | повторное обсуждение, невыполнение, эскалация | хронология по пунктам, измеримые результаты, подтверждение, согласие по умолчанию через 2 рабочих дня |

Блок согласия по умолчанию (только официальный режим):

```markdown
Прошу подтвердить получение письма. Если у тебя есть замечания или возражения по зафиксированным договорённостям — напиши в ответ в течение 2 рабочих дней. При отсутствии возражений в этот срок договорённости, указанные в письме, считаем принятыми.
```

Относится только к договорённостям в письме, не к HR-решениям. Возражения сотрудника фиксируются отдельно.

## Формат даты в заметках

Конспект: `03.07.2026` → заметка: `03.07.2026`

## Приватная секция follow-up

Сценарий `1в` пишет в `{slug}/follow-up.md`.

Это приватный контур для тимлида. Он не должен автоматически попадать в общий текст письма сотруднику.

Шаблон записи:

```markdown
ДД.ММ.ГГГГ
  * **Контекст:** [после какого 1:1 / follow-up]
  * **Режим письма:** [мягкий / официальный]
  * **Договорённость:**
    * [суть]
  * **Срок:** [дата / период / `-`]
  * **Статус:** [выполнено / частично / не выполнено / перенесено / в работе]
  * **Факт по статусу:**
    * [что произошло фактически]
  * **Обсуждали повторно:**
    * [когда и как вернулись к теме] / `-`
  * **Следующий шаг / новая договорённость:**
    * [что договорились делать дальше]
  * **Письмо:**
    * тема: [тема]
    * отправлено: [дата] / `[заполнить после отправки]`
  * **Ответ сотрудника:**
    * [ответ / возражения / `-`] / `ответа не было`
  * **Согласие по умолчанию:**
    * [дата] / `-`
```

Правила:

- только проверяемые факты;
- без ярлыков и домыслов;
- если срок не назывался, писать `-`;
- если был повторный срыв, фиксировать это по датам, а не общими формулировками;
- «согласие по умолчанию» — только после истечения срока из официального письма и при отсутствии возражений.

## Контекст с других встреч (архитектура)

### Рекомендация: отдельный скилл `meeting-context`

Сканировать `~/Downloads/` при каждой подготовке к 1:1 — **не стоит**:
- много файлов, медленно;
- смешивает две задачи (майнинг конспектов и подготовка 1:1);
- Downloads — временная папка, не структурированное хранилище.

**Лучше два скилла:**

| Скилл | Задача | Когда запускать |
|-------|--------|-----------------|
| `meeting-context` | Сканирует конспекты в Downloads, находит реплики людей из `notes/teams/`, дописывает в `{slug}/meeting-context.md` | Раз в неделю, или «обнови контекст по команде», или перед блоком 1:1 |
| `1-1` | Читает `meeting-context.md` **с даты последнего 1:1** при подготовке | Перед каждым 1:1 |

### Файл `meeting-context.md`

Копится целиком. Формат блока — в скилле `meeting-context`.

Правила наполнения:
- только групповые встречи (не 1:1 — те обрабатывает сценарий 1);
- только рабочие реплики человека;
- с датой и кратким названием встречи;
- дописывать; при повторном прогоне на ту же дату+встречу — обновить блок;
- при подготовке к 1:1 читать **с даты последнего 1:1**.

### Связка скиллов

```
Downloads (.txt)  →  meeting-context  →  {slug}/meeting-context.md
                                                    ↓
{slug}/README.md + 1-1.md + meeting-context.md  →  1-1 (подготовка)
                         ↑
jira-employee-analysis → reports/employees/  (по подтверждению; краткий блок в чат/повестку)
```

Опциональные поля в карточке для Jira: `Jira username`, `Jira account id` (см. `_template.md`). Если пусто — резолв имени через CLI/`people_aliases` (скилл `jira-employee-analysis`).
