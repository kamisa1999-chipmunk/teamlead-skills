# Примеры Story-prep

Читать только если нужен образец формулировок. Не подставлять примеры в живую Story как факты.

## Команды

Новая Story:

```text
подготовь story по этой хотелке
заведи DeliveryStory по этой странице
story prep
сделай нормальную story по этому описанию
создай story, дополнительно учти: ...
```

Переработка:

```text
перепиши CAT2-XXXX по правилам story-prep
приведи эту story в нормальный вид
проверь и переработай существующую story
очисти постановку от технического решения
```

## Требование vs hypothesis

Исходник:

```text
Frontend передаёт segmentId в ticker-api, backend фильтрует тикеры.
```

Внутренне: `SOLUTION_HYPOTHESIS`, не `REQUIREMENT`.

В ожидаемом поведении:

```text
Пользователь видит только тикеры, применимые к его сегментации.
```

В «Идеи / гипотезы для анализа», если вариант нельзя терять:

```text
Есть предпочтение рассмотреть вариант: витрина передаёт segmentId, backend фильтрует.
Альтернатива: backend сам определяет сегменты пользователя.
Не выбранное решение.
```

Плохо: «в обсуждении решили делать через segmentId» / «команда склонялась к этому варианту», если такого источника нет.

## Продуктовый edge case, не технический

Плохо как requirement:

```text
Если segmentId пустой, API возвращает тикеры с null в поле segment.
```

Хорошо как вопрос или, если подтверждено, как поведение:

```text
Что видит пользователь, который не входит ни в один сегмент?
Что показывать, если у тикера сегмент не указан?
```

## Компактный черновик

```markdown
*Контекст / проблема*
Нельзя показать тикер только выбранной группе. Сейчас либо всем, либо скрытие на одном экране вручную.

*Цель*
Контент управляет показом тикера через segmentation rules.

*Ожидаемое поведение*
- У тикера можно указать сегмент или оставить пустым.
- Пустой сегмент — тикер виден всем, кто проходит прочие настройки показа.
- Пользователь видит свои сегментные тикеры и тикеры без сегмента; чужие — нет.

*Scope*
Тикеры / перетяжки, которые контент уже настраивает.

*Out of scope*
Внешний вид плашки.   ← только если подтверждено

*Идеи / гипотезы для анализа*
Есть предпочтение рассмотреть вариант: витрина передаёт сегмент в существующий клиент тикера, как cityId. Не выбранное решение.

*Открытые вопросы*
Неблокирующие:
- Несколько сегментов у тикера и у пользователя — какой продуктовый результат?
Предварительно (устно): teens = «не показывать никакие тикеры» — не подтверждено.

*Ссылки / источники*
…

Черновик постановки подготовлен с использованием AI по указанным источникам и проверен автором Story.
```

Плохо: писать «бренды, скорее всего, не входят» в Out of scope как факт.  
Хорошо: открытый вопрос «бренды в scope?» или ничего, пока нет подтверждения.

## Rewrite: существенные изменения

На CAT2-4279 типичный набор:

```text
Схема «витрина прокидывает segmentId» перенесена в «Идеи / гипотезы»: предпочтение / вариант реализации, не требование и не решение команды.
Сохранено продуктовое правило: тикер без сегмента виден всем, с сегментом — своей группе.
«Бренды, скорее всего, не входят» не записано в Out of scope — оставлен вопрос.
Добавлена provenance-строка.
```

Не писать в diff внутренний лог поиска.

## Provenance: предпочтение ≠ решение

Плохо:

```text
В обсуждении решили делать фильтрацию на backend.
Команда склонялась к тому, чтобы не трогать клиенты.
```

Хорошо, если это сказал пользователь в текущем диалоге:

```text
Есть предпочтение рассмотреть backend-вариант, чтобы уменьшить клиентскую логику и количество запросов с клиентов.
Не выбранное решение.
```

Плохо: подтверждённый факт «сейчас сегмент не передаётся в тикер-API» оставить открытым вопросом или развить в «значит, нужно расширять контракт».

Хорошо: факт — в контексте как current state; способ реализации — в идеях / открытых вопросах, пока не подтверждён.

Плохо: в ожидаемом поведении молча выбрать один из неподтверждённых вариантов («тикер виден только первому сегменту пользователя»).

Хорошо: поведение с несколькими сегментами — открытый вопрос, пока продукт не подтвердил.
