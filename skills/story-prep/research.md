# Исследование для Story-prep

Читать **после исходных материалов**, до классификации. Не превращать в полный анализ системы. Глубокий impact analysis и проектирование — работа системного аналитика.

Нормальный flow:

```text
исходный материал → прямые ссылки → несколько целевых поисковых запросов → релевантные результаты
```

Остановиться, когда информации достаточно для качественной постановки Story либо становится понятно, какие вопросы надо задать пользователю/бизнесу.

## Уровень 1. Исходные материалы

Всегда начать с материалов, которые дал пользователь.

Определить:

- какую проблему хотят решить;
- кто инициатор / для кого изменение;
- текущее известное поведение;
- желаемое поведение;
- явно названные ограничения;
- ссылки и упоминания связанных сущностей.

В режиме `rewrite` существующая Story — один из источников этого уровня. Не считать весь её текст заведомо корректным требованием.

## Уровень 2. Прямые ссылки

Пройти прямые ссылки из исходного материала:

- Confluence;
- связанные Jira;
- документацию;
- явно указанные обсуждения;
- другие непосредственно связанные источники.

Не открывать нерелевантные ссылки.

## Уровень 3. Поиск по Confluence

Искать похожую или ранее описанную функциональность, даже если пользователь не дал прямой ссылки.

Сформировать несколько осмысленных поисковых запросов на основании:

- названия функции;
- бизнес-терминов;
- сущностей;
- названий экранов / сервисов / разделов;
- синонимов и старых названий, если они известны из контекста.

Цель поиска:

- найти старые требования;
- существующее описание текущего поведения;
- связанные инициативы;
- принятые ранее продуктовые ограничения;
- документацию похожего сценария.

Не считать найденную страницу автоматически актуальной.

Для каждого найденного материала оценить:

- действительно ли речь о той же функциональности;
- насколько материал свежий;
- не противоречит ли он более новым источникам;
- это требование, описание текущего состояния, историческое решение или просто идея.

Если найденный материал существенно влияет на Story — использовать его и указать источник.

Если найден старый конфликтующий материал — не выбирать самостоятельно «правильный» вариант без evidence; отметить конфликт.

Не исследовать весь Confluence. Несколько целевых запросов, затем релевантные результаты.

## Уровень 4. Jira

Проверять:

- прямые связи;
- задачи, на которые ссылаются найденные документы;
- предыдущую реализацию этой же функции;
- очевидно связанные Story.

Можно выполнить ограниченный поиск по Jira, если это помогает установить текущее поведение или найти предыдущую аналогичную реализацию.

Не использовать Jira-поиск как бесконечный discovery.

## Уровень 5. Код и технические артефакты

Использовать дозированно.

Разрешено подтверждать факты:

- функция существует;
- компонент действительно используется;
- есть общий клиент / сервис;
- текущее поведение реализовано определённым образом;
- существует указанный механизм.

Нельзя на основании исследования кода проектировать новую архитектуру и записывать её в Story как решение.

## Что искать в продуктовой постановке

Story Prep ищет пробелы именно в продуктовой постановке.

Примеры вопросов:

- Для каких пользователей действует изменение?
- Какие объекты / страницы / сценарии входят в scope?
- Что должно происходить по умолчанию?
- Что происходит, если настройка не задана?
- Может ли одновременно действовать несколько правил?
- Есть ли конфликтующие правила и каков ожидаемый продуктовый результат?
- Кто управляет настройкой?
- Нужны ли разные правила для стран / регионов / брендов / сегментов?
- Что должно остаться без изменений?
- Есть ли обязательные ограничения совместимости?
- Какое текущее проблемное поведение мы исправляем?

Не задавать на этом этапе вопросы типа:

- какой endpoint изменить;
- где хранить новое поле;
- какой сервис должен определять сегмент;
- какой контракт расширять;
- какая БД должна стать источником данных.

Если ответ на технический вопрос действительно является заранее утверждённым ограничением, его можно зафиксировать как constraint со ссылкой на источник.

## Edge cases

Самостоятельно подумать о крайних продуктовых сценариях.

Edge cases формулировать как продуктовые вопросы/поведение, а не как техническое решение.

Например для сегментации:

- пользователь не входит ни в один сегмент;
- входит в несколько сегментов;
- у объекта сегмент не указан;
- правила пересекаются;
- сегментация пользователя изменилась;
- существуют разные настройки для разных стран.

Не добавлять edge case в requirement как факт, если ожидаемое поведение не подтверждено.

Если поведение неизвестно — `OPEN_QUESTION`.
