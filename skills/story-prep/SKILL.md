# Story-prep

Подготовка DeliveryStory до начала системного анализа.

Story описывает, **ЧТО** и **ЗАЧЕМ** нужно изменить, а не **КАК** это технически реализовать.

Не проектирует решение за системного аналитика. Не пишет в Jira без подтверждения. Не подменяет `jira-write`.

Вымышленный черновик Story и папка фичи — `examples/features/items/01-reading-list/` (от этой папки: `../../examples/`). В Jira уходит description, не этот файл.

Не читать reference-файлы заранее. Каждый — только на своём этапе.

## Связка скиллов

| Skill | Ответственность |
| --- | --- |
| `feature-assessment` | быстрый разбор сырого запроса / feasibility / ownership / rough estimate |
| **`story-prep`** | продуктовая постановка DeliveryStory |
| `solution-research` | глубокая техническая проработка вариантов |
| `jira-write` | preview → подтверждение → create/update в Jira |
| `sa-task-prep` | постановка отдельной задачи системному аналитику |
| `sa-spec` | системная аналитика и спецификации |
| `sa-impact-analysis` | техническое влияние изменения |
| `sa-review` | проверка уже выполненной аналитики |

Story Prep заканчивает работу там, где сформулирована качественная продуктовая постановка и становится понятно, что именно должен исследовать системный аналитик.

Сырой запрос «прикинь как сделать / сколько займёт / это наша зона» — `feature-assessment`, не этот скилл. Не писать rough estimate вместо Story. Глубокий technical research вариантов — `solution-research`.

## Режимы

Определить режим **до** исследования.

| id | Когда |
| --- | --- |
| `create` | нет готовой Story; хотелка, Confluence, Epic/Feature, скриншот, заметки, обсуждение |
| `rewrite` | есть ключ Jira Story; «перепиши», «приведи в нормальный вид», «очисти от технического решения» |

Если пользователь дал и хотелку, и ключ существующей Story — `rewrite`, если просит привести карточку в порядок; иначе уточнить.

## Инварианты

- Story описывает ЧТО и ЗАЧЕМ, не КАК;
- `SOLUTION_HYPOTHESIS` нельзя незаметно превращать в requirement;
- предварительное (BRD без согласованных макетов, устная договорённость, неуверенный ответ) не превращать в requirement, constraint или факт Out of scope;
- существующее описание — один из источников, не заведомо корректное требование;
- не придумывать источник позиции и не повышать степень её согласованности;
- комментарий пользователя в текущем диалоге ≠ обсуждение; обсуждение ≠ согласованное решение;
- старая Story / BRD ≠ подтверждённое требование; найденный аналог ≠ источник требования;
- идея, предпочтение или гипотеза от пользователя — `есть предпочтение` / `пользователь предлагает рассмотреть` / `гипотеза` / `предпочтительное направление для анализа`, не решение команды;
- не писать `в обсуждении решили`, `команда склонялась`, `было согласовано`, если в источниках этого нет;
- не повышать `предпочтение` до `constraint` или `requirement` без подтверждения;
- пользовательские технические предпочтения — в «Идеи / гипотезы для анализа», не как коллективное решение;
- подтверждённый пользователем или разработчиком технический факт — `FACT` / confirmed current state, не open question; не развивать в implementation conclusion без основания;
- если существенная характеристика ещё не подтверждена, основной текст Story не должен молча фиксировать один из вариантов;
- полезные технические наблюдения не терять: если это не requirement — в «Идеи / гипотезы для анализа», без готовой архитектуры;
- текст Story компактный, без повторов; основной блок должен сканироваться;
- при конфликте источников не выбирать «правильный» вариант без evidence;
- не исследовать весь Confluence / всю Jira / всю систему;
- не задавать вопрос, на который отвечает явно доступный материал;
- технический вопрос не блокирует Story, если он не мешает сформулировать продуктовое поведение;
- не проектировать архитектуру и не записывать её в Story как решение;
- не публиковать в Jira автоматически;
- классификацию пользователю целиком не показывать.

## Pipeline

Идти по порядку. Внутреннюю модель не показывать.

```text
определить режим
→ исходные материалы              ← прочитать sources.md
→ прямые ссылки                   ← прочитать research.md
→ целевой поиск Confluence
→ ограниченный Jira
→ код только для FACT
→ классифицировать утверждения    ← прочитать classification.md
→ вопросы blocking / non-blocking
→ черновик Story                  ← прочитать story-format.md
→ (rewrite) существенный diff
→ статус READY / NEEDS_CLARIFICATION
→ показать пользователю
→ после подтверждения → jira-write
```

Копировать:

```text
Story-prep:
- [ ] Режим: create | rewrite
- [ ] Уровень 1: исходные материалы (sources.md)
- [ ] Уровень 2: прямые ссылки (research.md)
- [ ] Уровень 3: целевой поиск Confluence
- [ ] Уровень 4: ограниченный Jira
- [ ] Уровень 5: код только для FACT, если нужен
- [ ] Классификация (classification.md)
- [ ] Вопросы: blocking / non-blocking
- [ ] Черновик Story (story-format.md)
- [ ] (rewrite) существенный diff
- [ ] Статус READY / NEEDS_CLARIFICATION
- [ ] Показ пользователю
- [ ] После подтверждения: jira-write
```

### 1. Режим и исходные материалы

Прочитай `sources.md`. Собрать всё, что дал пользователь: текст, ссылки, ключ Jira, скриншот, заметки, комментарии.

В режиме `rewrite` прочитать существующую Story выбранным источником. Считать её источником, не истиной.

Зафиксировать: проблему; инициатора / для кого; текущее поведение; желаемое поведение; явные ограничения; связанные сущности.

### 2. Исследование

Прочитай `research.md`. Дальше — только направленный поиск:

1. прямые ссылки из исходного материала;
2. несколько целевых запросов в Confluence;
3. связанные и очевидно релевантные Jira;
4. код — только чтобы подтвердить FACT.

Остановиться, когда информации достаточно для постановки **или** понятно, какие вопросы задать.

### 3. Классификация

Прочитай `classification.md`. Внутренне разметить существенные утверждения: `FACT` / `REQUIREMENT` / `CONSTRAINT` / `ASSUMPTION` / `SOLUTION_HYPOTHESIS` / `OPEN_QUESTION`.

Не показывать эту разметку целиком без необходимости.

### 4. Вопросы и черновик

Прочитай `story-format.md`. Сформировать компактный текст Story и список вопросов.

- `BLOCKING` — без ответа нельзя однозначно сформулировать бизнес-поведение.
- `NON-BLOCKING` — Story можно завести, вопрос сохранить.

1–5 вопросов за итерацию. Сначала источники, потом вопросы.

### 5. Показ и Jira

Показать черновик. В `rewrite` — только существенные изменения, затем полный новый текст.

`NEEDS_CLARIFICATION` → не вызывать `jira-write`, пока пользователь не закроет blocking-вопросы или явно не решит завести Story с открытыми пробелами.

`READY` → после «да / создай / обновляй / применяй» открыть `jira-write` и передать summary + description. Самому Jira API не вызывать.

Постановку отдельной SA-задачи этим скиллом не собирать — это `sa-task-prep`.

## Запреты

Нельзя: проектировать техническое решение и писать его как requirement; терять полезные hypothesis; обходить весь Confluence; использовать Jira-поиск как бесконечный discovery; задавать технические вопросы про endpoint / БД / сервис / контракт, если это не утверждённый constraint; автоматически менять Jira; дублировать pipeline `sa-review`; писать runtime-state в tracked-файлы.
