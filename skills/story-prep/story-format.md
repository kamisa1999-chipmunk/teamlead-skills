# Формат Story и показ пользователю

Читать **перед черновиком и первым пользовательским выводом**. Не читать в начале прогона.

Финальный текст Story должен быть компактным и легко сканироваться. Не делать документ объёмом системной спецификации. Перед финальной строкой прочитай [provenance.md](provenance.md).

## Вопросы пользователю

Skill может и должен задавать вопросы, если без них невозможно корректно сформировать Story.

Но:

- сначала самостоятельно изучить доступные источники;
- не задавать вопрос, на который можно получить ответ из явно доступного материала;
- группировать связанные вопросы;
- задавать только те вопросы, которые влияют на содержание Story;
- избегать длинного questionnaire.

Предпочтительно 1–5 вопросов за итерацию.

Если вопрос можно оставить на системный анализ и он не мешает определить продуктовый requirement — не блокировать создание Story.

Разделять:

- `BLOCKING` — без ответа нельзя однозначно сформулировать требуемое бизнес-поведение.
- `NON-BLOCKING` — можно завести Story, но вопрос стоит сохранить для дальнейшего уточнения.

## Компактность

- Один факт — один раз: не повторять цель в контексте и в ожидаемом поведении.
- Списки вместо абзацев.
- Убирать пояснения «это решит SA», если то же следует из раздела идей или открытых вопросов.
- Основной блок (контекст, цель, поведение, scope) должен читаться за несколько секунд.
- Не раздувать идеи до архитектуры.

## Структура текста Story

Рекомендуемая структура:

```markdown
*Контекст / проблема*
Боль и текущее поведение. Коротко.
Подтверждённый пользователем или разработчиком технический факт текущего устройства — сюда как current state, не в открытые вопросы.

*Цель*
Один-два предложения: какой результат нужен.

*Ожидаемое поведение*
Только подтверждённые продуктовые правила, без реализации.
Если существенная характеристика ещё не подтверждена — не фиксировать молча один из вариантов в этом блоке.

*Scope*
Если известен и полезен. Не дублировать цель.

*Out of scope*
Только явно подтверждённое.
Неподтверждённые исключения сюда не писать как факт — в открытые вопросы.

*Ограничения / зависимости*
Только подтверждённые constraints.

*Идеи / гипотезы для анализа*
Необязательный. Найденные или переданные технические варианты — коротко.
Пользовательские технические предпочтения сохранять здесь, не выдавая за коллективное решение.
Если идея пришла от пользователя: `есть предпочтение` / `пользователь предлагает рассмотреть` / `гипотеза` / `предпочтительное направление для анализа`.
Явно: это не выбранное решение. Не детализировать до готовой архитектуры.
Не развивать подтверждённый факт в дополнительный вывод о реализации без основания.

*Открытые вопросы*
Только актуальные. Blocking и non-blocking — если есть смысл.
Предварительное (BRD без макетов, устное, неуверенный ответ) — сюда, с пометкой «предварительно».

*Ссылки / источники*
Основные релевантные материалы. Без длинного списка.

Черновик постановки подготовлен с использованием AI по указанным источникам и проверен автором Story.
```

Последняя строка — только если в `provenance.md` стоит `enabled: true`. Иначе не добавлять.

Раздел `Идеи / гипотезы для анализа` не обязателен. Добавлять, только если иначе потеряется полезная hypothesis. Не заменять им ожидаемое поведение.

Если существенная характеристика ещё не подтверждена, основной текст (контекст, цель, поведение, scope) не должен молча фиксировать один из вариантов — в открытые вопросы или идеи.

Не включать:

- выбранный архитектурный вариант как requirement;
- список сервисов / API / коллекций «для реализации»;
- impact analysis;
- критерии приёмки, выдуманные за продукт;
- оценку часов.

Summary предлагать коротко, в духе существующих DeliveryStory (`[DLV] …`), не выдумывая платформенный prefix Development-задачи.

## Статус готовности

Перед предложением создать / обновить Jira определить один из статусов.

### READY

Story достаточно определена для передачи в системный анализ.

Могут оставаться non-blocking вопросы.

Не требовать технической определённости для статуса `READY`.

Story может быть `READY` даже если пока неизвестны:

- конкретные сервисы;
- изменение API;
- архитектурный вариант;
- источник некоторых технических данных.

Это работа системного анализа.

### NEEDS_CLARIFICATION

Есть продуктовые пробелы, без которых Story фактически допускает несколько разных требований.

Показать вопросы и не писать в Jira без дальнейшего решения пользователя.

## Режим переработки существующей Story

Дополнительно сформировать внутренний diff:

- что сохранено;
- что уточнено;
- что удалено как неподтверждённое;
- что перенесено из requirement в идеи / гипотезы;
- что оставлено предварительным, а не записано в Out of scope;
- какие новые вопросы обнаружены;
- какие новые источники найдены.

Пользователю показать только существенные изменения.

Например:

```text
Из постановки убрана конкретная схема передачи segmentId: она является вариантом реализации, а не бизнес-требованием.
Добавлен вопрос о пользователях, входящих одновременно в несколько сегментов.
Найдена ранее существовавшая документация X, из неё добавлено ограничение Y.
```

После этого показать полный новый текст Story.

## Показ пользователю

Русские названия. Не показывать внутренние id категорий, чеклист pipeline и лог поиска, если не просили технический отчёт.

```text
Режим: новая Story | переработка CAT2-XXXX
Статус: готова к анализу | нужны уточнения

Существенные изменения:   ← только rewrite
- …

Черновик Story
…

Вопросы
Блокирующие:
- …
Неблокирующие:
- …

Основные источники
- …

Создать / обновить в Jira?
```

Блок «Существенные изменения» не ставить в `create`.

Для `NEEDS_CLARIFICATION` не предлагать сразу apply. Сначала вопросы. Если пользователь явно просит завести карточку с открытыми пробелами — тогда `jira-write`, сохранив вопросы в тексте Story.

## Передача в jira-write

`story-prep` не реализует Jira API.

Flow:

```text
story-prep → показать черновик → пользователь подтверждает → jira-write создаёт или обновляет DeliveryStory
```

Не изменять Jira автоматически. При rewrite подтверждение тоже обязательно.

Передать в `jira-write`:

- тип `DeliveryStory` (алиасы `delivery` / `dlv` в project config);
- proposed summary;
- полный description;
- известные epic / links / labels — только если они уже есть в контексте или их явно назвал пользователь;
- в rewrite — ключ задачи и diff description.

Не выдумывать assignee, estimate, sprint, критерии приёмки. `issue-creation-rules.md` читает `jira-write`, не этот скилл.

После подтверждения открыть `~/.cursor/skills/jira-write/SKILL.md` и выполнить preview → apply.
