# Solution-research

Глубокая техническая проработка решения для фичи или технической проблемы.

Не только для системных аналитиков. Могут использовать team lead, разработчик, SA, архитектор — любой, кому нужно разобраться в техническом решении.

Главная задача:

> Исследовать существующую систему достаточно глубоко, чтобы команда могла осознанно выбрать техническое решение и использовать результаты исследования дальше в разработке.

На выходе — **папка фичи** в `notes/features/items/<nn>-<slug>/`: живая заметка, technical design package и схемы. Не россыпь файлов и не research без канона для решений.

Вымышленная папка той же формы — `examples/features/items/01-reading-list/` (от этой папки: `../../examples/`). Живые фичи — в `notes/features/`.

Не пишет Story. Не ставит SA-задачу. Не пишет полноценные спецификации. Не публикует в Jira / Confluence. Не меняет production code. Не читать reference-файлы заранее. Каждый — только на своём этапе.

## Связка скиллов

```text
сырой запрос → feature-assessment → solution-research
```

`solution-research` умеет запускаться независимо.

Отдельная цепочка, не зависит насильно:

```text
story-prep → sa-task-prep → sa-spec → sa-review
```

| Skill | Ответственность |
| --- | --- |
| `feature-assessment` | быстрый разбор сырого запроса / feasibility / ownership / rough estimate |
| **`solution-research`** | глубокая техническая проработка вариантов |
| `story-prep` | продуктовая постановка DeliveryStory |
| `sa-task-prep` | постановка задачи системному аналитику |
| `sa-spec` | системная аналитика и спецификации |
| `sa-review` | review выполненного системного анализа |

`feature-assessment` отвечает: «что нам принесли, какой подход выглядит разумным и сколько примерно это может стоить?»

`solution-research` отвечает: «как система реально устроена, какие варианты жизнеспособны, чем они отличаются и какое решение имеет смысл выбрать?»

После показа пакета не запускать другие скиллы автоматически. Можно предложить: зафиксировать `DECISION`, `story-prep` / `sa-task-prep`, либо follow-up задачи — без создания в Jira.

## Вход

Любой набор, не обязательно полный:

- Jira Story;
- Jira Analysis / SA Task;
- feature note;
- ссылка на Confluence;
- technical question;
- результат `feature-assessment`;
- текстовое описание пользователя;
- комбинация источников.

Примеры:

```text
проработай техническое решение по CAT2-4279
сделай solution research по сегментации тикеров
сравни эти два варианта и посмотри код
как лучше реализовать эту фичу?
```

Известные варианты и предпочтения пользователя — `USER_INPUT` / `OPTION`, не выбранное решение.

## Provenance

В результатах различать:

| Метка | Что это |
| --- | --- |
| `FACT` | подтверждено кодом / документацией / системой |
| `USER_INPUT` | передано пользователем |
| `ASSUMPTION` | допущение |
| `INFERENCE` | вывод на основании найденных фактов |
| `OPTION` | вариант реализации |
| `OPEN_QUESTION` | требует проверки |
| `DECISION` | только явно принятое решение |
| `RECOMMENDATION` | рекомендация skill, не решение |

Не повышать статус информации.

Комментарий пользователя ≠ командное решение.  
Найденный аналог ≠ выбранная архитектура.  
Текущий код ≠ требование для новой реализации.  
Рекомендация skill ≠ принятое решение.

Подробности — в `classification.md` на шаге нормализации.

## Pipeline

Идти по порядку. Внутреннюю модель и лог поиска не показывать.

```text
понять задачу                    ← прочитать sources.md, classification.md
→ feature context / скелет папки  ← прочитать skeleton.md
→ Jira / Confluence
→ локальные репозитории          ← прочитать research.md
→ current state
→ impact map
→ варианты и сравнение           ← прочитать options.md
→ recommendation
→ (если явно выбран) decision
→ вопросы
→ technical design package       ← прочитать output-format.md, skeleton.md
→ сохранить папку фичи
```

Копировать:

```text
Solution-research:
- [ ] Задача / scope / известные варианты (sources.md, classification.md)
- [ ] Каноническая папка фичи: items/<nn>-<slug>/ (skeleton.md)
- [ ] Целевой Jira / Confluence
- [ ] Релевантные репозитории, не все (research.md)
- [ ] Current state + evidence
- [ ] Impact map — только релевантное
- [ ] Известные варианты включены; новые — только с основанием
- [ ] Каждый существенный вариант проверен по системе
- [ ] Comparison
- [ ] Recommended option = RECOMMENDATION, не DECISION
- [ ] (если пользователь явно выбрал) DECISION
- [ ] Open questions / assumptions
- [ ] Technical design package (output-format.md)
- [ ] Сохранить скелет: живая заметка + solution-research.md + puml
```

### 1. Понять задачу

Прочитай `sources.md` и `classification.md`. Собрать:

- какую проблему решаем;
- business / product behavior;
- scope;
- известные ограничения;
- известные варианты;
- уже принятые решения;
- вопросы.

Story или SA Task — источники, не абсолютная истина.

### 2. Feature context и скелет папки

Прочитай `skeleton.md`. Определить канонический путь `notes/features/items/<nn>-<slug>/` — существующая папка, одиночный md который переедет в папку, или новый номер.

Если живая заметка есть: прочитать; использовать историю решений и встреч; не создавать вторую заметку и не дублировать бизнес-контекст в research.

Если папки ещё нет — это нормально. Файлы писать в конце прогона, но путь зафиксировать сейчас. Не оставлять research без папки фичи.

### 3. Jira / Confluence

Целевой поиск, не бесконечный: текущая документация, аналоги, связанные технические задачи, предыдущие архитектурные решения, API specs, service pages, admin specs, ограничения, миграции / исторические решения.

### 4. Локальные репозитории

Прочитай `research.md`. Это одна из основных функций skill.

Сначала определить релевантные репозитории, затем исследовать. Не сканировать все без необходимости.

Для существенных технических утверждений сохранять evidence: `repo → path → symbol / class / method`. Большие куски кода не копировать.

### 5. Current state и impact

Восстановить техническую картину и собрать impact map. Универсальный список областей не копировать — только реально релевантное. Для каждого impact — evidence или причина inference.

Схемы current/target — в папку фичи по `skeleton.md`. Формат по умолчанию PlantUML. Mermaid не использовать автоматически.

### 6. Варианты, comparison, recommendation

Прочитай `options.md`. Известные варианты обязательно включить. Новые — только с техническим основанием.

Каждый существенный вариант проверить по реальной системе. Сформировать компактное сравнение и `Recommended option`.

Рекомендация остаётся `RECOMMENDATION`, не `DECISION`. Архитектуру молча не выбирать.

Если пользователь явно выбрал вариант — зафиксировать `DECISION` в живой заметке. После этого target-state из recommendation становится выбранным контуром; можно актуализировать impact и next. До явного выбора `target-state.puml` — схема рекомендации, не решения.

### 7. Вопросы, оценка, показ

Сначала исследовать доступные источники. Затем 1–5 вопросов за итерацию: `blocking` / `non-blocking`. Если можно продолжить с assumption — продолжить и явно записать.

Оценивать сроки не обязательно. Если пользователь просит или исследование началось после `feature-assessment` — можно обновить rough estimate. Разделять engineering effort и calendar / delivery estimate. Assumptions и confidence обязательны. Не выдавать за официальную оценку команд.

Прочитай `output-format.md` и ещё раз `skeleton.md`. Показать пакет пользователю. Сохранить **папку фичи**: живая заметка, `solution-research.md`, `current-state.puml`, `target-state.puml`.

Существующую живую заметку не переписывать с нуля: добавить ссылки, статус, recommendation (не решение). Таблицу Decisions менять только после явного «берём / зафиксируй». Recommendation в Decisions не поднимать.

## Что skill НЕ должен делать

Не должен:

- превращать пользовательскую идею в согласованное решение;
- выбирать архитектуру без маркировки recommendation;
- переписывать Story;
- выполнять функцию `sa-task-prep`;
- писать полноценные спецификации вместо команды;
- автоматически заводить Jira-задачи;
- менять production code;
- создавать Mermaid без подтверждения;
- придумывать ownership без evidence;
- выдавать inference за факт;
- оставлять research или диаграммы сиротами вне папки фичи;
- записывать recommendation в таблицу Decisions;
- копировать бизнес-контекст из живой заметки в research-файл;
- исследовать весь монорепозиторий и несвязанные сервисы.

## Запреты

Нельзя: принимать комментарий пользователя как командное решение; записывать recommendation как DECISION; публиковать в Jira / Confluence; менять production code; писать runtime-state в tracked-файлы; оптимизировать разбор под конкретный живой CAT2 из обсуждения скилла.
