# Скелет папки фичи для Solution-research

Читать **на шаге feature context** и ещё раз **перед записью файлов**. Это обязательная часть прогона, не опция.

Technical design package живёт в папке фичи. Не оставлять `solution-research.md` сиротой в `notes/features/items/` и не разбрасывать `.puml` рядом без папки.

## Обязательная структура

Каждый прогон `solution-research` заканчивается такой папкой:

```text
notes/features/items/<nn>-<slug>/
  <nn>-<slug>.md          # живой feature note: статус, решения, ссылки
  solution-research.md    # technical design package
  current-state.puml      # как устроено сейчас
  target-state.puml       # как будет при recommended option
```

Имена файлов фиксированные. Не называть research `ticker-segmentation-research.md` и не класть диаграммы в `items/diagrams/`.

`<nn>` — двузначный номер из индекса фич. `<slug>` — короткий kebab-case по сути фичи, латиницей.

Пример: `13-ticker-segmentation/`.

## Кто за что отвечает

| Файл | Канон для | Не класть сюда |
| --- | --- | --- |
| `<nn>-<slug>.md` | статус, цель, Jira, таблица **Decisions**, открытые вопросы, ссылки | весь current state, comparison, evidence по коду |
| `solution-research.md` | current state, impact, варианты, comparison, recommendation, evidence | полный бизнес-контекст из живой заметки |
| `current-state.puml` | схема текущего контура | целевое состояние |
| `target-state.puml` | схема **рекомендуемого** контура | принятое решение, пока его не зафиксировали |

`RECOMMENDATION` остаётся рекомендацией. В таблицу Decisions живой заметки её не поднимать.

## Как найти или завести папку

На шаге feature context — сначала resolve путь, файлы писать в конце прогона.

1. Есть папка `items/<nn>-<slug>/` — использовать её. Второй папки на ту же фичу не создавать.
2. Есть одиночный файл `items/<nn>-<slug>.md` — это та же фича. В конце прогона **перенести** в папку `items/<nn>-<slug>/<nn>-<slug>.md`, не переписывая содержимое с нуля. Добавить блок «Материалы» и ссылку на research. Обновить ссылку в `notes/features/all-features-list.md`.
3. Папки и файла нет — завести новые `<nn>` и `<slug>`.
4. Несколько кандидатов — не угадывать. Спросить или явно выбрать по Jira / названию и записать, почему.

Новый номер: посмотреть файлы и папки в `items/` (и строки индекса), взять следующий свободный `nn`. Не переиспользовать номер другой фичи. Не сдвигать чужие номера.

Новый slug: 2–4 слова по сути, латиница, без даты и без CAT2-ключа в имени папки.

## Что создать обязательно

### Живая заметка `<nn>-<slug>.md`

Если файла ещё нет — создать по шаблону ниже. Если есть — не уничтожать структуру: дополнить статус, материалы, recommendation (не решение), вопросы. Таблицу Decisions трогать только если в этом прогоне пользователь явно сказал «берём / зафиксируй».

Не копировать в заметку весь design package.

### `solution-research.md`

Всегда. Содержимое — по `output-format.md`. В шапке — ссылка на живую заметку и Jira.

### PlantUML

По умолчанию оба файла:

- `current-state.puml` — текущие вызовы / компоненты;
- `target-state.puml` — контур **recommended option**, в title явно что это recommendation, не decision.

Пропустить диаграмму только если рисовать нечего (нет контура, чисто табличное сравнение без потоков). Тогда в чате одной строкой сказать, какого файла нет и почему. Не рисовать диаграмму ради галочки. Mermaid — только после явного подтверждения, правила в `output-format.md`.

Дополнительные `sequence.puml` и т.п. — по пользе, в ту же папку.

## Шаблон живой заметки

Только для **новой** заметки. Существующую не заменять этим каркасом.

```markdown
# <nn>. <Название>

← [К оглавлению](../../all-features-list.md)

> Живой файл фичи: статус, решения, ссылки.
> Технический design package — отдельно, не копировать сюда целиком.

## Цель

<потребность, не выбранная архитектура>

## Заказчик / участники

| Роль | Кто |
|------|-----|
| … | … |

## Jira

- …

## Статус (ДД.ММ.ГГГГ)

- …

## Материалы

Всё по фиче лежит в этой папке.

| Что | Где |
|-----|-----|
| **Этот файл** | канон: решения, статус, вопросы |
| Solution research | [solution-research.md](./solution-research.md) |
| Current / target | [current-state.puml](./current-state.puml), [target-state.puml](./target-state.puml) |

## Платформы

| Слой | Scope |
|------|--------|
| … | … |

## Решения

Пока **нет** принятых архитектурных решений.

Сюда писать только явное «берём / зафиксировали». Recommendation из research сюда не поднимать.

| Дата | Решение | Источник |
|------|---------|----------|
| — | — | — |

## Recommendation (не решение)

<кратко: какой option рекомендует research. Не писать как решение.>

Подробности — в [research](./solution-research.md).

## Открытые вопросы

- …

## Out of scope

- …

## Next

- [ ] Зафиксировать архитектурный option (или явно отклонить recommendation).
```

Пустые секции вроде «Заказчик», которых нет в источниках, не выдумывать — убрать или оставить «неизвестно».

## Индекс и соседние ссылки

Если завели новую нумерованную фичу или перенесли файл в папку:

- обновить ссылку в `notes/features/all-features-list.md` на `./items/<nn>-<slug>/<nn>-<slug>.md`;
- не переписывать чужие строки индекса.

Если у фичи уже есть карточка wishlist / абзац в плане квартала — добавить ссылку на папку или живую заметку. Существующие заметки не переписывать.

Другие markdown в `features/` и `teams/` этим скиллом не трогать без нужды.

## Миграция одиночного файла

```text
items/13-foo.md  →  items/13-foo/13-foo.md
```

Относительные ссылки внутри заметки после переноса поправить (`../all-features-list.md` → `../../all-features-list.md` и т.п.). Старый путь в корне `items/` не оставлять. Дубликатов `*research*.md` вне папки не оставлять.

## Запреты

Нельзя:

- сохранить только `solution-research.md` в корне `items/`;
- создать папку без живой заметки;
- записать recommendation в таблицу Decisions;
- скопировать весь research в живую заметку;
- создать вторую папку / второй номер на ту же фичу;
- молча выбрать архитектуру, нарисовав target-state как свершившийся факт.
