# Исследование системы для Solution-research

Читать **после понимания задачи и feature context**, до вариантов. Это основная глубина skill: восстановить current state и impact по реальной системе.

Глубже, чем `feature-assessment`. Не заменяет `sa-spec`: спецификации не писать.

Остановиться, когда:

- current state достаточно подтверждён;
- варианты можно предметно сравнить;
- ключевой impact понятен;
- оставшиеся неизвестные явно зафиксированы.

Не читать весь монорепозиторий. Не исследовать несвязанные сервисы. Не искать бесконечно. Не создавать архитектурную документацию всей системы.

## Порядок

```text
feature notes → целевой Jira/Confluence → релевантные репозитории → current state → impact
```

## Feature notes

Живой контекст — папка `notes/features/items/<nn>-<slug>/` (или пока ещё одиночный md в `items/`). Использовать, не дублировать.

Сначала смотреть внутри папки фичи: живая заметка, уже существующий `solution-research.md`, `*.puml`. Общий `items/diagrams/` — только если на фичу ещё нет своей папки.

Существующие решения из заметки — кандидаты в `OPTION` или `DECISION` только при явном подтверждении в тексте. Recommendation прошлого прогона ≠ `DECISION`.

## Jira / Confluence

Целевые запросы по названиям сущностей, сервисов, экранов, контрактов и известным синонимам.

Искать: текущую документацию, аналогичные реализации, связанные технические задачи, предыдущие архитектурные решения, API specs, service pages, admin specs, ограничения, миграции.

Несколько осмысленных запросов, затем релевантные результаты. Найденная страница ≠ актуальная истина.

## Локальные репозитории

Сначала определить релевантные, затем исследовать. Не сканировать все без необходимости.

### Где искать

Ориентир локальной машины пользователя (проверять наличие, не считать обязательным списком):

```text
~/Desktop/Projects/backend/<service>/
~/Desktop/Projects/web/
~/Desktop/Projects/web-admin/
~/Desktop/Projects/ios/
~/Desktop/Projects/android/
```

Также — репозитории, уже открытые в workspace или явно указанные пользователем.

Типичные слои, если они относятся к задаче: backend, web, iOS, Android, admin, BFF, contracts, другие сервисы.

Не ходить по всем проектам на диске «на всякий случай». Нет доступа к репозиторию — `OPEN_QUESTION`, не выдумывать устройство клиента или сервиса.

### Как выбрать репозиторий

1. Из задачи понять затронутые слои и сущности.
2. Сопоставить с доступными каталогами / workspace.
3. Открыть 1–N релевантных репозиториев.
4. Искать точечно: grep / glob / чтение entry points.
5. Расширять поиск только если evidence ведёт в соседний сервис.

### Что искать

Только относящееся к задаче:

- entry points;
- сервисы;
- shared clients;
- handlers / use cases;
- API calls;
- DTO / contracts;
- domain models;
- persistence;
- filters;
- feature flags;
- integration points;
- существующие аналоги;
- обработку backward compatibility;
- места использования.

Список — ориентир, не чек-лист для копирования в ответ.

### Evidence

Для каждого существенного технического утверждения по возможности:

```text
repo → path → symbol / class / method
```

Пример формата, не шаблон под все фичи:

```text
catalog-web/src/.../TickerClient.ts → requestTicker()
```

Не копировать большие куски кода без необходимости. Путь и символ важнее цитаты.

Разрешено подтверждать `FACT`: механизм существует; текущий вызов идёт через конкретный клиент; данные хранятся там-то; похожее решение уже используется.

Нельзя на основании кода: объявить найденный аналог обязательным способом; записать текущую реализацию как требование для новой.

## Current state

Ответить:

- какие компоненты участвуют;
- кто кого вызывает;
- какие данные передаются;
- где хранится состояние;
- где выполняется бизнес-логика;
- какие клиенты используют механизм;
- где уже существуют похожие решения.

Результат оформить как `Current state`. При необходимости — диаграмма (правила в `output-format.md`).

Неподтверждённые звенья цепочки — `INFERENCE` / `OPEN_QUESTION`, не дорисованная архитектура.

## Impact map

Показывать только реально релевантное. Универсальный список в ответ не копировать.

Проверять применимое влияние на:

- backend;
- web;
- iOS;
- Android;
- admin;
- BFF;
- contracts;
- databases;
- caches;
- search / facets;
- ranking / recommendations;
- external integrations;
- analytics;
- backward compatibility;
- rollout;
- documentation;
- ownership других команд.

Для каждого impact — evidence или причина inference. Маркер уверенности: `confirmed` / `likely` / `possible`.

Не придумывать ownership без evidence. Если команда неизвестна — `OPEN_QUESTION` / `INFERENCE`, не «это точно команда X».

## Backward compatibility

Для изменений контрактов, API, данных или поведения проверить:

- старые версии приложений;
- клиенты без новых полей;
- отсутствие нового контекста;
- default behavior;
- rollout разных платформ в разные даты.

Если compatibility неактуальна — блок не нужен.

## Technical vs delivery complexity

Не смешивать:

- **Technical complexity** — сложность самой реализации.
- **Coordination / delivery complexity** — количество команд, зависимостей, последовательность релизов, организационный overhead.

Пример смысла: технически изменение небольшое, но требует несколько команд / сервисов, поэтому календарный срок выше инженерного effort.
