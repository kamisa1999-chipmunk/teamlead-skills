# Варианты, сравнение и recommendation

Читать **после current state и impact**, до показа пакета. Не выбирать архитектуру за пользователя.

## Известные варианты

Если варианты были предложены пользователем, указаны в Story, найдены в feature notes или обсуждались ранее — обязательно включить их в исследование.

Не превращать их в выбранное решение.

Маркировать источник: `USER_INPUT` / Story / feature note / прошлый груминг. Предпочтение пользователя — предпочтение, не `DECISION`.

## Новые варианты

Skill может предлагать дополнительные варианты, если для них найдено техническое основание: существующий механизм, аналог, ограничение текущей архитектуры.

Не генерировать варианты «для количества». Нет основания — не добавлять Option N.

## Исследование вариантов

Каждый существенный вариант проверить по реальной системе, а не только теоретически описать.

Для каждого варианта определить **применимые** характеристики. Использовать только релевантные критерии:

- что потребуется изменить;
- какие компоненты затрагиваются;
- какие команды затрагиваются;
- изменения контрактов;
- изменения данных;
- client impact;
- backend impact;
- backward compatibility;
- performance;
- scalability;
- coupling;
- duplication of logic;
- rollout complexity;
- maintenance;
- risks;
- dependencies;
- migration;
- observability.

Универсальную таблицу критериев в каждый option не копировать. Пустые строки не держать.

Разделять technical complexity и coordination / delivery complexity.

## Comparison

Компактное сравнение. Не делать огромные таблицы ради формальности.

Пример структуры:

| Критерий | Option A | Option B |
|---|---|---|
| Backend changes | ... | ... |
| Client changes | ... | ... |
| New integrations | ... | ... |
| Old clients | ... | ... |
| Coupling | ... | ... |
| Delivery complexity | ... | ... |
| Risks | ... | ... |

Строки — только те, по которым варианты реально различаются или различие важно для выбора.

## Recommendation

В отличие от `sa-task-prep`, `solution-research` **может давать рекомендацию**.

Сформулировать `Recommended option` и объяснить:

- почему;
- при каких assumptions;
- какие trade-offs принимаются.

Рекомендация остаётся `RECOMMENDATION`, не `DECISION`.

Не записывать решение как принятое, пока пользователь / команда явно не подтвердили его.

Плохо:

```text
Выбранный вариант: фильтровать на BFF. Это решение команды.
```

Хорошо:

```text
Recommended option: фильтровать на BFF.
Почему: один слой, существующий клиент, старые приложения сохраняют текущее поведение.
Assumptions: сегмент уже доступен BFF; отдельный сервис не нужен.
Это рекомендация, не принятое решение.
```

## Decision

Если пользователь явно выбрал вариант — зафиксировать `DECISION` в таблице Decisions живой заметки. В `solution-research.md` тоже отметить, что option выбран.

`target-state.puml` до выбора — схема recommendation. После выбора — тот же контур уже как принятый; title/пометку обновить.

Не выбирать архитектуру молча от имени пользователя. «Выглядит лучше» ≠ подтверждение. Recommendation в таблицу Decisions не копировать.

## Оценка

Не обязательна.

Давать или обновлять, если пользователь просит **или** исследование началось после `feature-assessment`.

Разделять:

- **engineering effort** — объём реализации;
- **calendar / delivery estimate** — срок с учётом координации и релизов.

Формат: диапазон (`S` / `M` / `L` / `XL` или спринты, если просили спринты). Confidence только `low` / `medium` / `high`. Assumptions обязательны.

Не выдавать за официальную оценку команд.
