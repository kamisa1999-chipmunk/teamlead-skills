# Формат SA Task и показ пользователю

Читать **перед черновиком и первым пользовательским выводом**. Не читать в начале прогона.

SA Task должна быть:

- компактной;
- легко сканируемой;
- без повторов;
- без длинных AI-рассуждений;
- с короткими смысловыми блоками.

Не дублировать одну и ту же мысль в `Цели`, `Что требуется проработать` и `Критерии завершения`.

Задача должна позволять руководителю после завершения однозначно проверить наличие результата.

Не использовать размытые формулировки:

- `посмотреть`
- `изучить`
- `подумать`
- `разобраться`

Предпочитать:

- `определить`
- `сравнить`
- `выбрать и обосновать`
- `зафиксировать`
- `обновить`
- `создать`
- `приложить ссылки`

При этом не задавать аналитику конкретную последовательность работы.

## Структура SA Task

### 1. Контекст

Коротко, 2–4 предложения.

Не копировать всю Story.

Указать:

- какую бизнес-задачу решает изменение;
- ссылку на DeliveryStory;
- важные ограничения, если без них непонятна задача;
- confirmed current state, если пользователь или разработчик уже подтвердил технический факт — не повторять его как вопрос анализа.

### 2. Цель анализа

Одна чёткая формулировка того, что системный аналитик должен определить.

Пример:

> Определить и обосновать техническое решение для применения segmentation rules к тикерам и подготовить изменение к разработке.

Не писать готовый технический способ реализации.

### 3. Что требуется проработать

Это основной содержательный блок задачи.

Он должен быть специфичен именно для текущей Story.

Типовые категории (ориентир, не чек-лист для копирования):

- определить технический scope;
- определить затронутые компоненты;
- определить необходимые изменения интеграций;
- определить изменения API / контрактов / данных;
- определить влияние на клиентские приложения / backend / admin;
- проверить обратную совместимость, в том числе отдельно для старых версий клиентов / приложений, если изменение контракта или поведения может на них повлиять;
- получить и зафиксировать ответы на продуктовые вопросы, влияющие на техническое решение;
- выявить зависимости и риски.

Не генерировать полный универсальный чек-лист.

Не дублировать SA-checklist.

Каждый пункт — проверяемый результат (`определить… и зафиксировать`, `сравнить… и выбрать с обоснованием`), без указания «как именно идти». Не включать пункты, которые к этой Story не относятся.

Не формулировать повторно как предмет анализа технический факт, который пользователь или разработчик уже подтвердил: использовать как confirmed current state.

Побочные возможности (например AB-тесты): если это не цель Story — сформулировать исследовательский вопрос `разобрать, позволяет ли выбранный вариант реализовать X и что для этого потребуется` и явно отметить, что это не requirement. Эту формулу не считать запрещённым «разобраться».

### 4. Варианты / гипотезы для анализа

Если в Story есть `Идеи / гипотезы для анализа`, перенести их сюда.

Правила:

- это не выбранные решения;
- аналитик должен рассмотреть их;
- при необходимости может предложить дополнительные варианты;
- по каждому существенному варианту нужно зафиксировать плюсы, минусы, ограничения и риски;
- выбранный вариант должен быть обоснован.

Не развивать гипотезы сильнее, чем они сформулированы в Story.

Не придумывать новые варианты без основания только ради количества.

В блоке гипотез сохранять мотивацию пользователя точно по смыслу, но не приписывать её команде или несуществующему обсуждению.

Плохо: `в обсуждении склонялись к backend-варианту`.

Хорошо: `есть предпочтение рассмотреть backend-вариант, чтобы уменьшить клиентскую логику и количество запросов с клиентов`.

Формулировка должна оставлять свободу для самостоятельного решения.

Если гипотез в Story нет — блок опустить или написать, что известных вариантов нет и аналитик определяет решение сам. Не заполнять выдуманными альтернативами.

### 5. Документация / спецификации

Это отдельная важная функция skill.

Формат блока:

### Найдено

- [Ticker] — страница сервиса
- [Segmentation rules] — описание механизма сегментов
- [API specification X] — если найдена

### Не найдено / требуется проверить

- API-контракт Ticker
- описание административной настройки
- описание клиентского контракта

Статус ненайденного: `Не найдено, требуется проверить наличие`.

Под списком «Не найдено» обязательно дописать правило (один раз, не повторять у каждой строки):

> Если отсутствие подтвердится и документ применим к выбранному изменению по SA-checklist — создать или актуализировать его по соответствующему шаблону в рамках этой задачи.

Не утверждать, что документа «нет», пока аналитик это не подтвердил.

Не предлагать по умолчанию выносить документацию в отдельную неблокирующую задачу.

Не требовать создавать документы, которые после анализа не относятся к выбранному решению.

### 6. Открытые вопросы

Сюда входят вопросы, которые:

- влияют на техническое решение;
- ещё не закрыты в Story;
- аналитик должен получить и зафиксировать ответы в рамках анализа — продуктовые уточнить у продукта.

Продуктовые дыры (неполное поведение, конфликтующий scope, неясный крайний случай) — это открытые вопросы SA, не повод переписывать Story и не повод стопать постановку.

Пометить продуктовые отдельно, чтобы было видно: закрываются уточнением у продукта, а не техническим исследованием.

Не дописывать недостающее продуктовое поведение как уже принятое требование.

Не писать `закрыть продуктовые вопросы`, если решение должен принять продукт. Использовать: `получить и зафиксировать ответы на продуктовые вопросы, влияющие на техническое решение`.

### 7. Критерий завершения

Не дублировать полный SA-checklist.

Использовать короткую формулировку:

> Задача считается готовой после выполнения применимых требований SA-checklist и прохождения self-check.

Дополнительно обязательно:

- в Jira приложены ссылки на итоговые / обновлённые / созданные спецификации;
- выбранное решение и его обоснование зафиксированы;
- блокирующих вопросов для передачи в разработку нет.

Не повторять второй раз полный список требований из блока `Что требуется проработать`.

## Показ пользователю

Русские названия. Не показывать внутренний чеклист pipeline и лог поиска, если не просили технический отчёт.

```text
Story: CAT2-XXXX

Предупреждение:          ← только если карточка пустая или уже есть Analysis
- …

Черновик SA Task
…

Создать Analysis в Jira?
```

Продуктовые вопросы внутри черновика — не блокер apply. Стоп только если Story нет или карточка пустая: предложить `story-prep`.

## Передача в jira-write

`sa-task-prep` не должен самостоятельно реализовывать Jira API.

Flow:

```text
DeliveryStory → sa-task-prep → показать черновик → подтверждение → jira-write создаёт SA-задачу
```

Без подтверждения Jira не менять.

Передать в `jira-write`:

- тип `Analysis`;
- summary: `[SA] <тема анализа>` (`R-SUM-SA`) — тема из цели анализа, не копировать summary Story один в один;
- description: полный текст 7 блоков (wiki Jira: `*Заголовок*`, списки; не сжимать до старого шаблона «цели / контекст / вопросы»);
- component: `SA`;
- связь с DeliveryStory: Sub task / Main task (`R-LINK-04`);
- epic / labels — только если уже есть в контексте или их явно назвал пользователь.

Не выдумывать assignee, estimate, sprint, критерии приёмки. Testing не создавать (`R-SA-06`). Чек-лист закрытия SA в description не копировать. `issue-creation-rules.md` читает `jira-write`, не этот скилл.

После подтверждения открыть `~/.cursor/skills/jira-write/SKILL.md` и выполнить preview → apply.
