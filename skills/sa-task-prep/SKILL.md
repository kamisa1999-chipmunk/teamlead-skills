# SA-task-prep

Готовит постановку задачи системному аналитику по существующей DeliveryStory.

Skill должен:

- собрать из Story и связанных источников контекст, который нужен системному аналитику;
- сформулировать проверяемую постановку задачи;
- зафиксировать, что именно требуется проработать;
- собрать известные технические гипотезы из Story;
- провести discovery по существующей документации и спецификациям;
- не проектировать решение за системного аналитика;
- не дублировать SA-checklist целиком.

Главный принцип:

> SA Task должна быть жёсткой по ожидаемому результату анализа, но не диктовать способ получения этого результата.

Не пишет в Jira без подтверждения. Не подменяет `jira-write`. Не читать reference-файлы заранее. Каждый — только на своём этапе.

Вымышленная постановка SA-задачи — `examples/features/items/01-reading-list/sa-task-draft.md` (от этой папки: `../../examples/`). В Jira её создаёт `jira-write` после подтверждения.

## Связка скиллов

| Skill | Ответственность |
| --- | --- |
| `feature-assessment` | быстрый разбор сырого запроса / feasibility / ownership / rough estimate |
| `story-prep` | качественная DeliveryStory |
| **`sa-task-prep`** | постановка отдельной задачи системному аналитику |
| `solution-research` | глубокая техническая проработка вариантов |
| `jira-write` | preview → подтверждение → create в Jira |
| `sa-spec` | системная аналитика и спецификации |
| `sa-review` | проверка уже выполненной аналитики |
| `sa-impact-analysis` | отдельный будущий skill для глубокого impact analysis |

Не смешивать ответственность. Не запускать `sa-spec`, `sa-review` и `solution-research` из этого скилла.

Сырой запрос без DeliveryStory и просьба «прикинь сроки / это наша зона» — `feature-assessment`, не этот скилл. Глубокий code research и сравнение вариантов — `solution-research`.

## Вход

Пользователь передаёт:

- ссылку / ключ DeliveryStory;
- при необходимости дополнительные комментарии.

Примеры:

- `подготовь SA-задачу по CAT2-4279`
- `создай задачу на системный анализ по этой Story`
- `sa task prep CAT2-XXXX`
- `подготовь постановку для системного аналитика`

Ключа нет — спросить. Тип не DeliveryStory, но карточка явно продуктовая — продолжить и отметить тип. Epic / Feature / хотелка без Story — не собирать SA Task; предложить `story-prep`.

Если на Story уже висит Analysis с той же целью — показать ключ, не создавать дубль молча. Спросить: обновить существующую или завести новую.

Продуктовые пробелы в Story не чинить и не отправлять по умолчанию в `story-prep`. Зафиксировать их открытыми вопросами: аналитик уточнит у продукта до выбора решения. `story-prep` — только если Story нет или карточка пустая и цель анализа сформулировать нельзя.

## Инварианты

- жёсткий ожидаемый результат анализа, свободный способ его получить;
- не выбирать архитектурный вариант и не расписывать готовое решение;
- не определять конкретные endpoint / таблицы / поля, если это ещё не подтверждено;
- не делать полный impact analysis;
- не писать спецификацию вместо аналитика;
- не превращать техническую гипотезу в обязательное решение;
- не придумывать источник позиции и не повышать степень её согласованности;
- комментарий пользователя в текущем диалоге ≠ обсуждение; обсуждение ≠ согласованное решение;
- старая Story / BRD ≠ подтверждённое требование; найденный аналог ≠ источник требования;
- идея, предпочтение или гипотеза от пользователя — `есть предпочтение` / `пользователь предлагает рассмотреть` / `гипотеза` / `предпочтительное направление для анализа`, не решение команды;
- не писать `в обсуждении решили`, `команда склонялась`, `было согласовано`, если в источниках этого нет;
- не повышать `предпочтение` до `constraint` или `requirement` без подтверждения;
- подтверждённый пользователем или разработчиком технический факт — confirmed current state, не предмет анализа повторно;
- обратная совместимость: отдельно учитывать старые версии клиентов / приложений, если изменение контракта или поведения может на них повлиять;
- побочные возможности (AB-тесты и т.п.), если это не цель Story — исследовательский вопрос, явно не requirement;
- не писать `закрыть продуктовые вопросы`, если решение должен принять продукт; использовать `получить и зафиксировать ответы на продуктовые вопросы, влияющие на техническое решение`;
- не дублировать Story целиком;
- не дублировать SA-checklist;
- `не найдено skill'ом` ≠ `документ точно отсутствует`;
- ненайденная документация: сначала `не найдено, требуется проверить наличие`; создавать или актуализировать в рамках SA-задачи только если отсутствие подтверждено и документ применим к выбранному изменению по SA-checklist; не предлагать по умолчанию отдельную неблокирующую задачу; не требовать документы, которые после анализа не относятся к выбранному решению;
- продуктовые дыры в Story → открытые вопросы SA, не переписывание Story;
- не исследовать весь Confluence / всю Jira / весь код;
- не публиковать в Jira автоматически.

## Pipeline

Идти по порядку. Внутреннюю модель и лог поиска не показывать.

```text
ключ Story
→ исходные материалы              ← прочитать sources.md
→ продуктовые пробелы → вопросы SA
→ прямые ссылки                   ← прочитать research.md
→ целевой поиск документации
→ ограниченный код (если нужен)
→ черновик SA Task                ← прочитать task-format.md
→ показать пользователю
→ после подтверждения → jira-write
```

Копировать:

```text
SA-task-prep:
- [ ] Ключ Story
- [ ] Уровень 1: Story + комментарии пользователя (sources.md)
- [ ] Продуктовые пробелы → открытые вопросы SA (не чинить Story)
- [ ] Уровень 2: прямые ссылки
- [ ] Уровень 3: целевой поиск документации (research.md)
- [ ] Уровень 4: код только для подтверждения компонента, если нужен
- [ ] Черновик SA Task (task-format.md)
- [ ] Показ пользователю
- [ ] После подтверждения: jira-write
```

### 1. Story и качество постановки

Прочитай `sources.md`. Собрать цель, поведение, scope / out of scope, ограничения, открытые вопросы, идеи / гипотезы, ссылки.

Продуктовые пробелы (неполное поведение, конфликтующие требования, техническая схема вместо «что/зачем», неясный scope) не чинить внутри SA Task и не стопать прогон. Перенести в открытые вопросы: аналитик доуточнит у продукта, прежде чем выбирать решение.

`story-prep` предлагать только если Story нет или карточка пустая — без цели нельзя сформулировать постановку.

Дополнительные комментарии пользователя — источник, не замена Story. Комментарий в текущем диалоге ≠ обсуждение и ≠ согласованное решение. Если пользователь или разработчик подтвердил технический факт — confirmed current state, не формулировать его повторно как предмет анализа.

### 2. Исследование документации

Прочитай `research.md`. Порядок:

1. прямые ссылки из Story;
2. документация связанных компонентов;
3. целевой поиск по Confluence/Jira;
4. только при необходимости — ограниченный поиск по коду для подтверждения существования компонента или интерфейса.

Глубокий анализ кода не делать. Не превращать этап в полный impact analysis.

Остановиться, когда достаточно сформулировать проверяемую постановку и карту найденной / ненайденной документации.

### 3. Черновик и Jira

Прочитай `task-format.md`. Сформировать компактный текст SA Task.

Показать черновик. Без подтверждения Jira не менять.

После «да / создай / применяй» открыть `~/.cursor/skills/jira-write/SKILL.md` и передать поля. Самому Jira API не вызывать.

Если пользователь прямо просит пакетное создание и ранее разрешил автоматическое обновление — использовать существующие правила `jira-write`.

## Запреты

Нельзя:

- выбирать архитектурный вариант;
- расписывать готовое решение;
- определять конкретные endpoint/таблицы/поля, если это ещё не подтверждено;
- делать полный impact analysis;
- писать спецификацию вместо аналитика;
- превращать техническую гипотезу в обязательное решение;
- дублировать полный SA-checklist;
- исправлять продуктовую Story молча;
- стопать постановку и отправлять в `story-prep` из‑за обычных продуктовых дыр;
- автоматически менять Jira.

Разрешено:

- собрать известный контекст;
- подсветить существующие компоненты;
- найти документацию;
- перечислить вопросы, ответы на которые нужно получить и зафиксировать, — в том числе продуктовые, влияющие на техническое решение;
- зафиксировать варианты, которые уже были предложены, без повышения до согласованного решения;
- сформулировать проверяемый результат задачи.
