# Discovery документации для SA-task-prep

Читать **после оценки Story**, до черновика. Не превращать в полный impact analysis и не проектировать решение.

Нормальный flow:

```text
Story → прямые ссылки → документация связанных компонентов → несколько целевых запросов → при необходимости код
```

Остановиться, когда можно сформулировать проверяемую постановку и заполнить блоки «Найдено» / «Не найдено, требуется проверить наличие».

## Приоритет поиска

1. прямые ссылки из Story;
2. документация связанных компонентов;
3. целевой поиск по Confluence/Jira;
4. только при необходимости — ограниченный поиск по коду для подтверждения существования компонента или интерфейса.

Глубокий анализ кода не делать.

## Что искать

- API docs;
- contract specs;
- сервисные страницы;
- функциональные спецификации;
- схемы данных;
- admin docs;
- связанные технические Confluence-страницы.

Для каждого **предположительно** затронутого компонента:

1. проверить наличие существующей документации;
2. проверить наличие спецификаций API / контрактов / схем данных / функциональных спецификаций;
3. если документ найден — приложить ссылку;
4. если документ не найден — не утверждать автоматически, что его нет.

Использовать статус:

> `Не найдено, требуется проверить наличие`

Важно:

> `не найдено skill'ом` ≠ `документ точно отсутствует`

Если аналитик **подтверждает отсутствие** документации, которая нужна для этого изменения **и применима к выбранному изменению по SA-checklist** — создать или актуализировать её по соответствующему шаблону в рамках SA-задачи. Не выносить создание документации в отдельную задачу со словами «не блокирует разработку». Не предлагать по умолчанию отдельную неблокирующую задачу. Не требовать создавать документы, которые после анализа не относятся к выбранному решению.

Не делать ложных утверждений. Не считать найденную страницу автоматически актуальной и не выбирать «правильный» документ при конфликте без evidence — отметить конфликт как вопрос для анализа.

## Уровень 1. Прямые ссылки из Story

Проверить:

- связанные Jira;
- Confluence;
- существующую документацию;
- API / контрактные спецификации;
- документацию сервисов;
- аналогичные технические решения, если они прямо связаны.

Не открывать нерелевантные ссылки. Связанная Analysis с той же целью — зафиксировать, не игнорировать.

## Уровень 2. Документация связанных компонентов

Компоненты брать только из Story, прямых ссылок и явно названных сущностей (сервис, сущность, экран, админка, контракт). Не строить полную карту экосистемы «на всякий случай».

Для названного компонента — целевой поиск страницы сервиса / спецификации / админки. 1–3 запроса на компонент, затем релевантные результаты.

## Уровень 3. Целевой поиск Confluence / Jira

Разрешён, если нужно:

- найти существующие спецификации;
- понять, какая документация относится к затронутому компоненту;
- найти существующие API / contract docs;
- найти текущую архитектурную документацию сервиса.

Несколько осмысленных запросов по названиям сущностей, сервисов, экранов и известным синонимам. Не исследовать весь Confluence. Не использовать Jira-поиск как бесконечный discovery.

Неполный поиск ≠ доказанное отсутствие документа.

## Уровень 4. Код

Только чтобы подтвердить FACT:

- компонент / интерфейс существует;
- у сущности есть клиент / контракт / схема.

Нельзя на основании кода:

- выбирать архитектурный вариант;
- перечислять конкретные endpoint / таблицы / поля как обязательный scope, если это не подтверждено документацией или явным constraint в Story;
- делать полный impact analysis.

## Что не искать на этом шаге

- полный список потребителей каждого метода;
- все версии контракта;
- все смежные фичи;
- «как правильно реализовать»;
- новые варианты решения, которых нет в Story.

Если в ходе поиска всплыла полезная техническая гипотеза, которой нет в Story — не добавлять её в варианты «ради количества». Можно кратко отметить в вопросах, только если она следует из найденного документа, а не из догадки.
